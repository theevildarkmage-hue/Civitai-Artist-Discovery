# Civitai Artist Discovery 2.0 project plan

## Purpose

Version 2.0 is a complete interface refresh inspired by Civitai's visual hierarchy and
interaction patterns while preserving this application's artist-first purpose. The work
also addresses slow perceived image loading, simplifies filters, and gives Daily Gallery,
Time Machine, and My Profile one shared interface system.

This is an implementation plan and restart record. Work should be completed one milestone
at a time, with the checkpoint updated before stopping so a later Codex session can resume
without rereading the entire repository or reconstructing earlier decisions.

## Product outcomes

2.0 succeeds when:

- The first useful gallery content appears quickly and image cards do not sit blank while
  avoidable requests complete.
- Daily Gallery feels familiar to a Civitai user but continues to group images by creator.
- Common feed, sort, and filter choices are understandable without documentation.
- Advanced discovery controls remain available without dominating the main toolbar.
- Daily Gallery, Time Machine, and My Profile share the same shell, cards, controls,
  loading states, dialogs, tokens, and responsive rules.
- Existing archives, account data, content controls, updates, reactions, follows, and
  collection behavior remain compatible.
- A 1.x bug fix can be developed and released while 2.0 is in progress.

## Non-goals

- Do not reproduce Civitai branding, proprietary artwork, or page structure exactly.
- Do not change the app from artist-first to a generic image feed.
- Do not migrate to React, Vue, or another framework solely for this redesign.
- Do not rewrite collection, ranking, authentication, or updater code unless a measured
  UI or performance requirement needs a focused change.
- Do not combine archive-building speed with preview-loading performance. They are
  separate experiences and should have separate metrics and messages.

## Delivery and branch strategy

Use these branch roles:

- `main`: releasable 1.x maintenance line. All urgent fixes start here and may ship as
  `1.0.5`, `1.0.6`, and so on.
- `v2`: integration branch for the redesign. Create it from the current `main` after this
  plan is accepted.
- Short-lived `v2/<milestone>-<topic>` branches are optional when a milestone is risky;
  merge them into `v2`, not directly into `main`.

For every 1.x fix made after `v2` branches:

1. Implement and verify the fix on `main`.
2. Release it from `main` if needed.
3. Merge `main` into `v2`, resolving the fix semantically rather than retaining obsolete
   1.x markup merely to avoid a conflict.
4. Run the focused regression test on `v2`.
5. Record the merged commit in the checkpoint log below.

Keep data/schema changes backward-compatible throughout development. A person who runs a
2.0 beta against their portable `data` directory should not be forced to abandon 1.x.
Prefer additive migrations. If an irreversible migration ever becomes necessary, 2.0
must first create and document a restorable backup.

The stable updater already excludes prereleases. Publish preview builds as
`2.0.0-beta.N`; do not change stable users to a beta update channel as part of this work.

## Architecture direction

The current UI is concentrated in `static/app.js`, `static/index.html`, and several CSS
files. Splitting code is part of 2.0, but it should be an incremental extraction, not a
framework rewrite.

Target browser-side structure:

```text
static/
  index.html                 minimal application mount points
  app.js                     startup and route/tab coordination only
  ui/
    api.js                   fetch wrapper and request cancellation
    state.js                 session state and subscriptions
    shell.js                 header, tabs, toolbar slots, account/update actions
    icons.js                 local reusable SVG icon functions
    menu.js                  dropdown/popover behavior and focus management
    filters.js               filter state, chips, count, reset, serialization
    cards.js                 shared artwork/creator card primitives
    gallery.js               paging, viewport loading, carousel coordination
    feedback.js              skeletons, empty/error states, progress, toasts
    dialog.js                shared modal behavior
  pages/
    gallery-page.js
    time-machine-page.js
    profile-page.js
  styles/
    tokens.css               color, type, spacing, radius, elevation, breakpoints
    base.css                 reset, typography, generic elements
    shell.css
    controls.css
    cards.css
    feedback.css
    pages/
      gallery.css
      time-machine.css
      profile.css
```

Native ES modules are sufficient because the app serves a modern local browser. Avoid a
bundler unless an implementation constraint is demonstrated. Shared modules should own
behavior as well as appearance: pages configure shared components rather than copying
their HTML and event handlers.

The server should continue to expose page-oriented endpoints, but common response shapes
should be normalized. Gallery and Time Machine cards should consume the same documented
creator/artwork view model where their capabilities overlap.

## Experience specification

### Shared application shell

- Compact dark header with app identity, installed version, account state, update state,
  and a clearly separated Close App action.
- One consistent primary navigation for Daily Gallery, Time Machine, and My Profile.
- A page toolbar slot below navigation. Toolbars remain sticky but use the same height,
  spacing, menu behavior, and active-state language on every page.
- Responsive behavior is designed at narrow phone, laptop, desktop, and wide desktop
  widths rather than patched page by page.
- All icon-only controls receive an accessible name, tooltip, visible focus state, and a
  minimum practical pointer target.

### Daily Gallery

- Preserve one card per creator and the image carousel.
- Make artwork the dominant surface: edge-to-edge preview, consistent rounded container,
  creator identity overlaid near the bottom, compact reaction/status strip, and secondary
  actions that do not compete with the image.
- Keep Follow and Open on Civitai easy to reach. Do not hide essential touch actions
  behind hover-only UI.
- Toolbar hierarchy:
  - feed/view menu: For You, Popular, Followed First, New to You, Emerging First;
  - time window/date control;
  - optional sort control only where it differs meaningfully from the feed choice;
  - Filters button with active count;
  - display/preferences gear.
- Display active filters as removable chips. Ordinary cached filters apply immediately.
- The filter panel initially exposes content level and generation model. High-volume
  thresholds and emerging ranking modes move to Advanced or Gallery Preferences.
- Keep the distinction between collection coverage and display filtering explicit only
  at build time; do not repeat that complexity during normal browsing.

### Time Machine

- Use the same artwork card, creator identity, reactions, follow action, details dialog,
  skeleton, image fallback, and seen-state conventions as Daily Gallery.
- Add Time Machine-specific progress as a card extension rather than a separate card
  implementation.
- Present priming/read-history status in the shared page header pattern.
- Clearly explain that scrolling advances the creator history before the behavior is
  enabled, and expose stop/retry actions through shared feedback components.

### My Profile

- Use the shared shell, page header, panels, buttons, pills, empty states, and responsive
  grid.
- Establish a clear hierarchy: profile summary first, suggested creators second,
  supporting taste/model/tag analytics after that.
- Reuse the shared creator row/card identity and Follow control for Worth Following.
- Move automatic collection, update settings, destructive reset, and other operational
  controls into a consistent Settings area instead of mixing them with profile insights.
- Keep analysis progress and stale/preliminary data states visible but compact.

## Performance requirements and measurement

Do not optimize from visual impression alone. Add inexpensive development instrumentation
before changing the pipeline and keep a repeatable fixture for comparison.

Measure at minimum:

- day-summary request duration;
- first artist-page response duration;
- tag/content-control verification duration and cache-hit ratio;
- time until first card skeleton;
- time until first preview request starts;
- time until first preview paints;
- number and transferred bytes of preview requests before first viewport settles;
- filter-to-first-new-preview duration;
- refresh-to-first-preview duration;
- long tasks and layout shifts during the first page.

Initial targets on a normal broadband connection with an already-built local day:

- Skeleton UI visible within 200 ms of a page/filter transition.
- First cached gallery response within 500 ms locally at the representative test size.
- First preview request starts within 300 ms when its safety decision is cached.
- First visible preview paints within 1.5 seconds under the reference network profile.
- Filter changes using local data show their first useful result within 750 ms.
- No more than two viewports of preview images are requested initially.
- No hidden-tag image is requested from the CDN before its visibility decision is known.

Final values should be adjusted after the baseline is recorded, but any change must be
documented rather than silently relaxing the target.

Likely implementation work, to confirm with measurements:

- Include known tag/content-control visibility in the artist-page response so the browser
  does not perform a second local request before assigning `src`.
- Batch or prepare unknown visibility decisions for the first page without serializing
  every visible preview behind an avoidable remote round trip.
- Reduce the initial artist page from 50 to an evidence-based size, likely 18–24, then
  page earlier with an adaptive viewport margin.
- Eagerly request only the first viewport; lazy-load subsequent rows.
- Serve/request preview widths appropriate to rendered card width and device density.
- Cancel or ignore obsolete requests consistently when filters change.
- Preserve/reconcile existing card DOM where a filter change does not require replacing
  it; otherwise render skeleton replacements immediately.
- Keep content-control safety invariant covered by `hidden_tags_before_preview.py`.

## Milestones

Each milestone ends with a clean commit, focused tests, an updated checkpoint, and no
known half-migrated component. Estimates are working days for one implementation agent
and include tests/review time.

### M0 — Baseline, fixtures, and decisions (1–2 days)

Deliverables:

- Capture reference screenshots of all three pages at phone, laptop, and wide desktop.
- Create a deterministic UI fixture or route stubs with enough cards and profile data to
  test without live Civitai requests.
- Record the performance baseline described above for fresh refresh, cached refresh,
  feed change, model filter, and content filter.
- Inventory behaviors covered by existing Playwright tests and identify selectors that
  should become stable `data-testid` or role-based queries.
- Confirm the card information hierarchy and filter taxonomy in a short decision record.
- Create `v2` from `main`.

Exit criteria: baseline numbers and screenshots are committed; no product behavior has
changed; the next session can implement tokens without rediscovering current behavior.

### M1 — Shared foundation and application shell (2–3 days)

Deliverables:

- Add design tokens, base styles, local icons, focus rules, and shared control/menu/dialog
  primitives.
- Introduce ES modules and move startup coordination out of the monolithic `app.js`
  without changing server behavior.
- Build the shared header/navigation/page-toolbar shell.
- Keep old page internals mounted inside the new shell temporarily.
- Add shell tests for navigation, keyboard operation, narrow layout, account state, update
  state, and Close App placement.

Exit criteria: all three pages navigate inside the same responsive shell; existing major
flows still pass; no page has its own duplicate header or menu implementation.

### M2 — Preview pipeline and measurable speed (2–4 days)

Deliverables:

- Add development timing instrumentation and a repeatable performance test fixture.
- Normalize the first-page API data needed to determine whether a preview may load.
- Implement first-viewport priority, smaller first page, skeletons, responsive preview
  sizing, stale-request cancellation, and progressive paging.
- Retain original-image fallback and content-control guarantees.
- Record before/after results in the checkpoint log or a linked performance report.

Exit criteria: performance targets are met or every miss has measured evidence and a
specific follow-up; hidden content cannot flash or download prematurely.

### M3 — Shared card system and Daily Gallery (3–4 days)

Deliverables:

- Create shared artwork, creator identity, reaction strip, follow action, status badge,
  carousel, and card-menu components.
- Convert Daily Gallery to the image-first card layout.
- Preserve reactions, follows, details, Civitai links, recommendations, seen behavior,
  card sizing, model filtering, and infinite paging.
- Make mouse, keyboard, and touch actions equivalent.
- Add visual/behavior tests at representative breakpoints.

Exit criteria: Daily Gallery no longer depends on the legacy card builder; all existing
gallery behaviors pass against the shared card system.

### M4 — Filter and feed simplification (2–3 days)

Deliverables:

- Implement the shared feed menu, date/window control, filter panel, active count, chips,
  reset behavior, and Gallery Preferences/Advanced area.
- Define a single serializable filter state model used by UI, session restoration, and
  API query generation.
- Apply cached filters immediately and provide visible pending/error states for anything
  that genuinely requires work.
- Preserve mature-content explicit opt-in and collection-coverage rules.
- Add tests for defaults, restoring state, clearing one/all filters, conflicting choices,
  keyboard focus, and narrow-screen panel behavior.

Exit criteria: a new user can reach the common feed/content/model choices from the main
toolbar; advanced controls no longer obscure those choices; restoration works.

### M5 — Time Machine conversion (1–2 days)

Deliverables:

- Render Time Machine through the shared card and page-header components.
- Add its progress/advance extension and shared priming feedback.
- Preserve ordering, hiding, advancement, persistence, reactions, follows, details, and
  empty-card removal.
- Update Time Machine Playwright coverage and responsive screenshots.

Exit criteria: no duplicate Time Machine card implementation remains; Time Machine-only
behavior is expressed as configuration or a small extension.

### M6 — My Profile conversion and settings organization (2–3 days)

Deliverables:

- Convert profile summary, panels, creator rows, pills, actions, progress, and empty/error
  states to shared components and tokens.
- Move operational preferences into a coherent Settings section/panel.
- Preserve analysis, refresh, hidden-preferences notice, auto-collection, update settings,
  Worth Following, and destructive reset behavior.
- Update dashboard and settings tests plus responsive screenshots.

Exit criteria: Profile uses the same shell and visual language, shared creator actions,
and feedback components; operational settings are clearly separated from insights.

### M7 — Integration, accessibility, and beta hardening (2–3 days)

Deliverables:

- Remove superseded markup, styles, event handlers, and compatibility shims.
- Test full first launch, existing-data upgrade, offline/read-only behavior, expired auth,
  errors, empty data, long usernames, missing avatars, broken previews, reduced motion,
  keyboard navigation, zoom, and supported screen sizes.
- Run the entire automated suite and a packaged Windows smoke test.
- Update README, release notes, Civitai page copy, screenshots, and version to
  `2.0.0-beta.1` only when the beta is ready to package.
- Document known beta limitations and rollback/data compatibility.

Exit criteria: no release-blocking regression; upgrade and rollback are understood; beta
artifact passes package/update validation.

### M8 — Beta feedback and stable 2.0 (elapsed time depends on feedback)

Deliverables:

- Triage beta reports into release blockers, later 2.x improvements, and unrelated v1
  fixes.
- Re-run performance measurements on realistic user data.
- Publish additional betas as needed without enrolling stable users automatically.
- Merge the accepted `v2` result to `main`, resolve documentation/versioning, run the full
  release checklist, and publish `2.0.0`.

Exit criteria: stable package and updater metadata are published; `main` is again the
single active release line; remaining work is in a 2.x backlog.

## Test strategy

Preserve the existing Python and Playwright suite. During extraction, prefer role/text
queries for user-visible behavior and stable test IDs only for otherwise ambiguous
components. Do not tie behavior tests to incidental CSS structure.

Required layers:

- Unit-level tests for filter serialization, state transitions, request cancellation, and
  server response normalization.
- Component/fixture tests for menus, chips, cards, carousel, follow/reaction state,
  skeleton/error transitions, and shared dialogs.
- Existing end-to-end flows for first launch, loading, content controls, filters, seen
  creators, Time Machine, profile, updates, and error recovery.
- Screenshot checks at approximately 390 px, 1366 px, and 1920 px widths for each page and
  major overlay. Keep approved reference images in a dedicated test artifact directory.
- Manual packaged smoke test because the normal browser test server does not exercise the
  tray, executable paths, updater, or real browser launch.

Every milestone runs its focused tests. M1, M3, M6, and M7 run the full suite because they
cross page boundaries or remove legacy code.

## Token-efficient execution and pause protocol

The implementation should be divided into small, restartable sessions. A session should
normally complete one task, not an entire milestone.

At the start of every session:

1. Read `docs/2.0-checkpoint.md`, `git status`, and the latest five commits. Read only the
   relevant milestone in this plan when its acceptance criteria are needed.
2. Read the files explicitly listed in `Next files`; do not rescan the whole repository
   unless the task or a failing test requires it.
3. Confirm the current branch and whether a newer `main` hotfix must be integrated.
4. State the single session objective and its acceptance check.

During the session:

- Prefer focused searches and tests.
- Keep changes within one component or vertical behavior slice.
- Do not mix cleanup unrelated to the acceptance check.
- Commit only after the focused test passes and the working tree contains no accidental
  files.

Before stopping for usage reset or any other reason:

1. Leave the repository in a buildable state whenever possible.
2. Update the checkpoint block with exact status, decisions, test commands/results,
   commit, modified files, and the next smallest action.
3. If work is intentionally uncommitted, describe each changed file and what remains;
   never make the next session infer intent from a diff alone.
4. Use the suggested resume prompt from the checkpoint. The next session should not need
   the previous chat transcript.

Recommended session size: one to three files, one focused test group, and one commit.

## Decision gates

Record review artifacts at these points. The user approved continuing implementation
while away on 2026-09-05; pending visual reviews do not block independent work. Publishing
beta or stable releases remains a separate action:

- After M0: approve information hierarchy, filter taxonomy, and reference direction.
- After M1: approve shared shell at phone and desktop widths.
- After M2: review measured performance improvement and any safety/latency tradeoff.
- After M3: approve final Daily Gallery card density and interactions.
- After M4: usability review of filters with someone unfamiliar with the current controls.
- After M6: approve the complete three-page visual system.
- Before beta packaging and before stable release.

Each review should have screenshots and a tested checkpoint that can be inspected when
the user returns. Document unresolved product choices and continue unrelated tasks.

## Risks and mitigations

- **Hidden-content flash:** Preview speed work must not assign a CDN URL until visibility
  is known. Preserve and extend the current regression test.
- **Monolithic-JavaScript regression:** Extract one behavior slice at a time and retain a
  compatibility entry point until its page is converted.
- **v1/v2 merge conflicts:** Keep fixes behavior-focused, merge `main` promptly, and avoid
  broad formatting rewrites.
- **Visual similarity without usability improvement:** Validate task flows and filter
  comprehension at decision gates, not just screenshots.
- **Large DOM and network burst:** Bound first-page size, observe actual card dimensions,
  and instrument request counts.
- **Feature loss during card reuse:** Maintain a capability checklist for Gallery and Time
  Machine and convert behavior through shared components before removing legacy code.
- **Portable-data incompatibility:** Use additive schema changes and test a copied 1.x data
  directory with both versions.
- **Scope expansion:** New discovery features go to a post-2.0 backlog unless required to
  make an existing behavior understandable.

## Definition of done for 2.0

- All milestone exit criteria are met.
- Full automated suite and packaged smoke tests pass.
- Performance report shows before/after measurements against agreed targets.
- Accessibility and responsive checks cover all pages and major overlays.
- No known hidden-content, account-data, archive, updater, or rollback regression exists.
- Shared UI code is used by all three pages; no copied card/menu/dialog implementation
  remains.
- User-facing and maintainer documentation is current.
- `2.0.0` is tagged, packaged, verified, and offered through the stable updater.
