# Private-beta invitation and moderation candidate

Local implementation only. No hosted deployment, policy, account, grant, network,
recommendation or release change is authorized by this document. The existing
staging baseline remains community-v1 version 10, owner-only and disabled.

## Admission and policy

The candidate production entry point fixes `invitationOnly:true` in code. Every
operation first verifies fresh Civitai UserInfo at the fixed OAuth hub. Only its
stable positive account ID is passed to database admission. Supabase Auth IDs,
body fields, query strings, headers and UI preferences are not invitation evidence.
Unexpected body fields are rejected. Missing migration/configuration, an unready
configuration, expired/revoked/missing invitations, and more than five current
invitations all fail closed. No invitation is seeded by the migration.

**The owner counts toward the five-person limit.** All participants, including the
owner and moderator when using member features, need an explicit unexpired invite.
An operator invite expires within 30 days; renewals are explicit audited actions.
Revoking an invite frees a slot and does not delete history. A global transaction
advisory lock serializes invitation changes, submitter blocks and member admission
before existing member/artist/image locks. Writes and same-key replay recheck
admission and blocks inside their own transaction, closing the check/write race.
This conservative serialization is appropriate to five members, not a large-scale
throughput design. Operations already committed before revocation remain accepted.

| Server state | Browse/status for invited members | Recommendation/preview/withdraw | Report |
|---|---|---|---|
| disabled/missing/unknown | Status only; gallery denied | Denied | Denied |
| read_only | Allowed | Denied | Allowed |
| enabled | Allowed | Allowed subject to blocks/quotas/verification | Allowed |
| owner_test | Status only in invitation candidate | Denied | Denied |

`enabled` is implemented and exercised locally, not enabled on staging. The old
owner-window factory option/tests remain for regression compatibility but are not
the candidate production entry point. An invitation is not a policy override.

Supabase-backed gallery/status reads always contact the server with the current
credential. The previous 24-hour canonical feed/status cache could mask denial,
revocation or moderation; it is not used as fallback for remote policy reads now.
Outages surface explicitly and never queue submissions silently. Local fixture
browsing and public artwork metadata/thumbnail caches retain their existing paths.
Previously downloaded public media cannot be recalled by a server policy change.

## Additive candidate migration and preservation

`supabase/beta-migrations/202610230001_private_beta_security.sql` is intentionally
outside the four pinned `supabase/migrations` files. Existing bootstrap tooling
must not silently discover it. It is a separate, single-transaction, one-shot
candidate requiring separate deployment approval and a new reviewed manifest.
It does not rewrite recommendation, member, accepted-audit or replay rows.

New private RLS tables in unexposed `community_private`:

- configuration: one fail-closed readiness row, initially false.
- operators: restricted database login to stable operator actor ID, expiry/revocation.
- invitations: account ID, expiry and revocation only.
- blocks: account ID and block state.
- reports: recommendation ID, reporter account ID, fixed reason, timestamp, decision.
- moderator_audit: authenticated operator ID/login, action, target, reason, timestamp.
- artwork_reviews: image ID, eligibility, verification/validity/lease times, lease
  nonce and bounded failure classification; no prompt, bearer token or full profile.

All direct private table/sequence rights are denied to anon, authenticated,
service_role and the operator group. No RLS policies grant ordinary access.
New functions explicitly revoke PostgreSQL's default PUBLIC EXECUTE. Helpers use
qualified private objects and fixed search paths. The original submit/quota/
withdraw/replay implementations are retained as revoked legacy routines; public
wrappers enforce admission. New replay handling explicitly calls the guarded
submit wrapper. The old unscoped gallery and old unaudited moderation RPC lose
service_role EXECUTE. Audits are preserved rather than assigned invented actors.
Legacy artwork starts pending revalidation and is temporarily withheld until checked.

## Reporting and submitter blocks

The member API accepts `report` with only artwork and a fixed reason:
inappropriate, abuse, ownership or unavailable. The desktop offers that dialog
only when authenticated status advertises reporting. An existing recommendation
is required, including a retained hidden/withdrawn record. One report per member
and recommendation is retained even after resolution; duplicate retries return
success without another row or daily budget consumption. New distinct reports are
limited to ten per 24 hours, in addition to token/member and report SQL throttles.
No free-text report, email, IP, prompt or bearer is stored. Reports never change
recommendation status automatically and are never returned by the public gallery.
Reporting remains available read-only to support abuse response; disabled denies it.

Blocks are global by verified account ID and persist across function/database
restarts. They deny preview, new recommendations and old successful replay before
quota or ledger writes. Existing recommendations remain in history but disappear
from new feed responses while blocked. Unblocking restores feed eligibility only
for independently active, freshly eligible records; it does not undo moderator
hide/remove actions. Blocked members may still browse and report while invited,
preventing a submitter restriction from silencing an abuse report.

## Separate moderator authority

Moderation is **not** a member HTTP operation or a Supabase service-key operation.
Use `scripts/community-operator.py` with a separately provisioned database LOGIN
that is a member of the restricted NOLOGIN/NOBYPASSRLS/NOINHERIT
`community_operator` group. That login has no direct table rights and cannot create
roles, change mappings, bypass RLS, or become another session identity. Do not grant
the group to PostgREST authenticator, service_role, anon or authenticated.

The public operator RPC has EXECUTE only for the operator group. It derives the
actor from `session_user` mapped in the private operators table, with expiry and
revocation checked on every call. `SET ROLE` does not change that authenticated
login. Neither a caller-supplied actor nor a Supabase/Civitai member identity grants
moderator rights. Operator actors are enrolled by a separately authorized database
administrator after identity verification; initial enrollment/revocation and login
provisioning require an external operator record. A compromised database owner
remains outside this restricted-operator threat boundary.

Supported actions: configure readiness; invite/revoke_invite; block/unblock;
hide/remove; resolve_report/dismiss_report; bounded paginated reports/audit reads.
Every state-changing action requires a 3-256 character reason and atomically appends
actor, login, action, target, reason and time. A failed audit insert rolls back the
action. Queue/audit reads return at most 50 rows after a sequence cursor and require
the same restricted authority. There is no browser moderator key or admin UI.

Operator credentials belong in a secure process/libpq environment, never command
arguments, source, chat or reports. The CLI sends SQL through stdin with literal
escaping, ignores psql startup files, suppresses SQL/credential error details and
never accepts an actor parameter. Remote use requires a separate approval,
`--allow-remote` and verified TLS. Use direct or verified session-mode connections
preserving the dedicated login; do not assume a shared role/transaction pool can
preserve the required session identity. Verify actual hosted custom-role login and
mapping before any deployment. No database password is retrieved in this task.

## Bounded artwork revalidation

Fresh submission verification still checks exact artwork, uploader, public/scanned
availability and allowed ratings before SQL writes. Feed eligibility lasts at most
15 minutes after successful verification. On a gallery read, database leases select
at most three due active artworks, ordered oldest-first, across all instances.
Exact-image verification uses at most two Civitai calls per artwork, in parallel
across the three leased artworks, with existing bounded response/timeout limits.
There is no background polling or unbounded batch loop.

Deleted/private/ineligible artwork, changed uploader and disallowed rating become
quarantined in the private projection. Transient failures also withhold expired
artwork, retrying after at least 60 seconds; definite failures wait 15 minutes.
Successful checks restore only eligibility, never a withdrawn/moderated status.
The 60-second lease has a random nonce, so expired workers cannot overwrite a newer
result. Gallery SQL independently requires a nonexpired eligible review and excludes
blocked submitters. All original attribution, quota, replay and accepted audit rows
remain intact. Rating/availability drift can remain visible until the next due
review, with a maximum 15-minute server eligibility window; already open/downloaded
media is not recalled. Desktop shared controls continue to apply independently.

A backlog can temporarily shorten/empty a page while due entries are withheld.
A later explicit refresh checks the next bounded batch. No automatic scanning is
added to fill an empty feed. Capacity/latency and user messaging for larger backlogs
remain operational acceptance items before increasing the cohort.

## Local validation and deployment boundary

Run the existing broad isolated application suite, five Node suites (including
`community_invitation_edge.mjs`), and the owned native runner with `--private-beta`.
That option first rehearses the candidate in an empty atomic-bootstrap database,
runs the original four-migration SQL/HTTP regressions, then applies the candidate
only in the disposable HTTP database and exercises the restricted operator login,
real member HTTP, simultaneous instances, report budgets, revocation, blocks,
concurrency/replay, revalidation leases, audit rollback and database recovery.
`--beta-only` is a focused iteration mode and is not the combined regression claim.
All identities are simulated. No hosted account/token/record is used.

Before a future deployment:

1. Review the final commit, candidate migration/hash, changed entry point and all
   RPC ACLs against the old four-migration baseline. Confirm dedicated operator
   role provisioning is supported by the exact hosted connection/authority.
2. Obtain explicit approval for schema, grants, function source and provisioning;
   keep COMMUNITY_BETA_STATE=disabled throughout bootstrap. Preserve encrypted
   backup and sanitized original catalog/hash evidence first.
3. Apply the candidate atomically with consistent migration-history recording.
   Do not rerun the original bootstrap over existing objects. Provision a dedicated
   mapped operator through an approved secret mechanism; no service-key fallback.
4. Deploy only the pinned function under that approval. Missing invitations/config
   remain denied. Enroll at most five stable IDs including the owner, with short
   expiries and audited reasons, only under the approved enrollment scope.
5. Repeat hosted direct-table/RPC denials, private-schema nonexposure, operator
   login/session identity, ordinary-user spoofing, revocation, limits and policy
   tests. Disabled must deny reports and recommendation writes. Take final hashes.
   The existing verify-hosted-community-security.py expects the version-10 seven-RPC
   baseline. Prepare/review a candidate-aware verifier for the new 17-RPC inventory
   and seven private RLS tables before hosted approval; do not weaken the baseline
   verifier or interpret its expected mismatch as missing management authority.
6. Complete backup restore, key rotation, cross-instance policy timing, privacy/
   retention and packaged dedicated-account acceptance before separately approving
   bounded writes. Local results do not authorize invitation activation or release.

Rollback is **disable and preserve**, not drop the new schema or restore old broad
grants. After this migration, version-10 function source is not a compatible
automatic rollback: its old gallery/moderation path is revoked and old members need
invitations. Prefer a reviewed compatible forward correction, keep history, and
request separate approval for any privilege or destructive recovery action.

Remaining operational blockers: hosted role/session compatibility, hosted backup
restore and accepted RPO/RTO, distributed invocation/cost controls, measured policy
propagation/incident drill, operator coverage, retention/deletion execution, privacy
notice, and packaged real-account/upgrade acceptance. Proposed report retention is
90 days and moderator audit one year, subject to explicit privacy review; no cleanup
job or unreviewed deletion is introduced here. Continue to cap the proposed first
cohort at five after those gates close.
