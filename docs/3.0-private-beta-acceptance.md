## Security and operational assessment

| Area | Verified implementation | Remaining beta gate |
|---|---|---|
| User reporting | No report endpoint or queue | Bounded authenticated reports, reason enums, deduplication, abuse limits and private triage required before invited writes |
| Submitter blocking | Viewer hidden/blocked preferences filter personal browsing | No durable service-wide submitter blocklist; enforce centrally on preview, submit and replay in the transaction, not only UI |
| Moderator authority | Service-only hide/remove RPC; public roles denied | No actor/reason audit or separate moderator identity/credential boundary; must implement before invited writes |

| Abuse | Per-token/member SQL buckets, quotas, body/time/response bounds and process concurrency limits | Gateway peer semantics and distributed ingress/cost protection unverified; per-isolate limit is not a global invocation budget |
| Retention | Minimal IDs/public names, time/status, audit and replay keys; no OAuth bearer in Community tables | Approve retention/deletion policy and scheduled cleanup; idle throttle buckets are not guaranteed wall-clock TTL |
| Policy propagation | Handler reads server environment per authenticated operation; missing/unknown policy fails closed | Prior owner read/restore checks do not establish maximum delay across warm/cold isolates or regions |
| Rotation/incident | Management credential in Windows Credential Manager; service credential remains server-only | Rehearse supported key rotation/revocation and operator handover without exporting secrets |

Seven RPCs remain executable by service_role, including community_moderate. Its

## Ranked blockers and cohort size

P0 activation boundaries: the deployed entry point is hardcoded owner-only, the
write window has expired, policy is disabled, and the production desktop endpoint
is unset. These are intentional safeguards. Changing a beta secret alone cannot
admit invitees safely; a reviewed server-side stable-ID invitation allowlist and
explicit production endpoint/build decision are required.

P1 before any invited submissions: reporting, durable submitter blocks,
actor/reason/time moderation audit and operator authorization; bounded handling of
deleted/rerated artwork; hosted backup restore drill; measured kill-switch
propagation and emergency containment; accountable operator coverage, alerts,
retention/privacy notice and abuse/cost controls.

P2 acceptance before distribution: packaged fresh dedicated-account OAuth,
refresh/revocation, upgrade/rollback on a clean Windows machine, invitee denial,
real multi-account hosted behavior, and measured latency/429/5xx/invocation costs.
Local signed test accounts and public metadata replay are not those verifications.

Recommended maximum initial cohort: **five invited testers after the applicable
gates close**, with a named moderator and daily review for the first week. This is
a conservative operational cap, not a demonstrated capacity. Current permitted
cohort remains the owner only, with hosted submissions disabled. Do not invite
20-50 writers on the strength of local tests. Read-only invitees could be reviewed
as a separate, smaller-scope milestone, but still require the allowlist, privacy,
read-policy and operational safeguards; this is not approved here.

## Exact controlled activation requirements

1. Approve the intended read-only or write-enabled cohort scope and stable-ID
   allowlist. Retain fresh Civitai UserInfo, fail-closed identity checks and a
   server-owned invitation boundary. Do not remove ownerOnly without its replacement.
2. Review local implementation and additive transactional migrations for reporting,
   blocking and moderator audit; include concurrency/replay/block enforcement,
   hostile moderator claims, grant/RLS and privacy/retention tests. Backfill legacy
   audit rows without inventing historical actors/reasons. Approval to prepare a
   design does not authorize applying it.
3. Close the P1 gates above, document RPO/RTO and incident contacts, and pass native
   SQL, real local HTTP, browser, packaging and hosted non-destructive acceptance.
4. Pin a new source commit, migration manifest/order/hashes, function source and
   configuration digests. Review exact credentials and rollback compatibility.
   Obtain separate deployment approval before any hosted operation that changes state.
5. Deploy disabled first only under that approval; verify source/history/grants/RLS,
   anonymous/authenticated denials, owner/invitee/non-invitee boundaries and absence
   of unexpected records. Then obtain separate approval for a bounded write test.
6. Only after its evidence and a separate activation/release approval, provision
   the reviewed endpoint/opt-in build and bounded cohort. Define owner, end time,
   measurement limits and stop conditions. Never enable general public submissions.

## Backup, rollback and incident procedure (not executed here)

Before a future rollout, export a consistent encrypted database backup through an
authorized connection using supported Supabase tooling. Keep credentials in a
secure process environment, dumps outside source control, access restricted and
retention bounded. Preserve schema, data, role/grant expectations and migration
history; inventory function source and secret names separately without exporting
secret values into reports. The platform's backup coverage depends on plan;
confirm it rather than infer it from a local dump.

Restore first to a separately approved disposable target, with outbound automation
disabled. Verify migration history, RLS/ACL/RPC catalog, row hashes/counts, quota,
audit/replay pairing and denial behavior before any traffic switch. Record elapsed
restore time and recovery point. Never restore over the staging ledger or reset
local databases to make a test pass. Proposed initial targets are RPO 24 hours and
RTO four hours; these require owner acceptance and a measured drill.

For an incident: preserve sanitized evidence, identify the operator and time,
stop rollout and request authorized disabled/read_only containment. Under a
separately approved emergency procedure, revoke both submit entry RPCs if secret
propagation is uncertain, as documented in 3.0-staging-runbook.md. This task does
not authorize those mutations. Verify denial across instances and inspect for
already-committed writes; a flag cannot undo them. Do not delete ledger/audit rows.

Restore a reviewed compatible function/app artifact only after approval. Prefer
additive forward correction for SQL; do not drop tables or replay bootstrap over
existing history. Rotate only the affected credential through supported dashboard
controls, verify the replacement server-side, revoke the old credential and test
that it fails. Management PAT rotation, service API credential rotation and Civitai
OAuth revocation are distinct operations. Never solve an incident by distributing
the service key, widening grants or silently reusing owner OAuth sessions.
