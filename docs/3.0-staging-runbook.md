# First authorized Supabase staging deployment (NOT EXECUTED)

All steps below require separate approval of project, region, budget, credentials
and dedicated test accounts. None creates a project or deploys during this milestone.
Never point these commands at a shared/daily-use installation or production database.

1. **Project and region.** An owner with MFA creates a new staging-only Supabase
   project in an explicitly selected region near the initial test cohort. Record
   project ref, owner, PostgreSQL version, budget/plan and incident contact privately.
   Free can support early bounded functional testing but has pause/backup limits;
   any paid plan or extra project needs approval. Do not equate local PG17.11 with
   the host's default version/extensions. No Storage bucket/Realtime is required.
2. **Secrets.** Keep the project database password and service-role credential in
   the approved server secret store only. SUPABASE_URL and reserved variables are
   supplied by the platform; verify the chosen service-key format against PostgREST.
   Never put privileged credentials in desktop configuration. Set
   COMMUNITY_BETA_STATE=disabled and COMMUNITY_ALLOWED_RATINGS=1,2. Use an external
   ignored env file with dashboard/CLI, never command history containing literal
   secrets. Supabase documents [secret provisioning](https://supabase.com/docs/guides/functions/secrets).
3. **Schema inventory.** Confirm an otherwise empty dedicated public schema, postgres
   ownership, expected anon/authenticated/service_role memberships and no unreviewed
   inherited grants. Snapshot default ACLs, version, extensions and indexes. Shared
   schemas are not supported without reviewing the third migration's CREATE revoke.
4. **Migrations.** Pin a reviewed commit and file hashes. Link only the approved ref,
   inspect the migration diff/dry-run, then apply in order using the CLI or a direct
   password-authenticated connection with ON_ERROR_STOP and --single-transaction
   per file. Do not apply on a persistent development SQLite database.

   ```powershell
   supabase link --project-ref <APPROVED_STAGING_REF>
   supabase db push --dry-run
   supabase db push
   ```

   Migration 202610140001 creates four tables, indexes, RPCs, RLS and privileges.
   It is one-shot: transaction replay rejects without partial schema changes.
   202610150001 adds replay keys/RPC and a fifth RLS table. Preserve accepted request
   keys on recovery; dropping them changes lost-response retry semantics.
   202610210001 hardens null checks and inherited ACLs and revokes public schema
   CREATE. It is repeatable. Local tests deliberately apply permissive grants first
   and reapply this migration; verify host default grants independently.
5. **Migration recovery.** Before any public writes, discarding the entire owned
   staging project and reapplying to a fresh approved project is the cleanest failed-
   bootstrap recovery, but deletion needs explicit approval. After data exists, take
   a tested backup and use an additive forward correction; never drop tables to
   resolve deployment errors. Reapply migration three for privilege hardening rather
   than restoring insecure defaults. There is no automatic destructive down script.
6. **Deploy Edge.** Review functions/community-v1/index.ts and handler.ts only; no
   tests/local_service.ts, dev modules, public member fixtures or local JWT keys.
   Confirm config.toml verify_jwt=false plus mandatory fixed-host Civitai UserInfo.

   ```powershell
   supabase functions deploy community-v1 --project-ref <APPROVED_STAGING_REF>
   ```

   Do not substitute Supabase Auth JWT checks for Civitai credentials. Deploying an
   unauthenticated wrapper without the independent UserInfo check is a blocker.
7. **Gateway/RLS.** Confirm no-token/invalid/local-test credentials fail on the deployed
   endpoint. Exercise anonymous and authenticated REST table SELECT/INSERT/UPDATE/
   DELETE and direct RPC denial; verify all five tables have RLS. Test ordinary role
   isolation with real hosted JWTs on a disposable staging transaction. Confirm only
   intended service RPC privileges, identity/sequence ACLs, schema CREATE restrictions
   and SECURITY DEFINER search paths. Never grant table access to make tests pass.
8. **Dedicated OAuth accounts.** Register/approve the appropriate public desktop
   client and exact loopback redirect/PKCE contract. Complete consent in the packaged
   app, verify fresh UserInfo sub/id, refresh rotation, expiration, revocation and
   logout/restart. Do not copy a rotating token between concurrently running clients.
   Test issuer/audience/client-binding assumptions and account recovery with the
   provider; opaque tokens cannot be locally decoded to settle these questions.
9. **Real ownership.** Use only those accounts and public eligible artworks. Reject
   own uploader IDs, missing/inconsistent owners, forged fields, deleted/unlisted/
   future/video cases and ratings outside 1,2. Accept eligible reciprocal images only
   in staging. Record trusted member/uploader IDs and sanitized responses, never tokens.
10. **Writes and races.** Keep state disabled until a bounded test window is approved.
    Temporarily enable for the dedicated cohort with network/cohort isolation agreed
    by the operator. Test three/member/week, three/artist/week, simultaneous last slots,
    duplicates, same-key retry (one record/audit), conflicting keys and lost responses.
    Verify accepted/audit/request rows after every race. Do not load-test Civitai.
11. **Incidents and limits.** Verify read_only permits cached/shared browsing and rejects
    all writes. Remove/mangle policy and confirm fail-closed. Measure secret propagation
    across warm/cold isolates; test timeouts and upstream outage without broad external
    disruption. Validate actual gateway peer addresses before trusting per-IP controls.
    Provision shared ingress/cost protection outside the function before public writes.
12. **Emergency stop.** Set COMMUNITY_BETA_STATE=read_only (or disabled). If propagation
    is uncertain, use an authorized database transaction to revoke BOTH entry points:

    ```sql
    begin;
    revoke execute on function public.community_submit(bigint,text,bigint,bigint,boolean) from service_role;
    revoke execute on function public.community_submit_once(bigint,text,bigint,bigint,text) from service_role;
    notify pgrst, 'reload schema';
    commit;
    ```

    Verify new writes fail via HTTP while quota/gallery reads survive. Revoking only
    the inner submit function does not disable a SECURITY DEFINER replay wrapper.
    Verify hosted role inheritance does not retain execution via another grant.
    Record operator/reason/time privately. Restore both intended EXECUTE grants only
    after an reviewed fix and tests; do not restore broad table/schema permissions.
13. **Backup/recovery.** Export an encrypted restricted-access PostgreSQL backup,
    test restoration to another approved disposable staging database, and compare
    recommendation/audit/replay counts and hashes. Plan log redaction/retention and
    an explicit recovery point objective. Platform backups depend on the selected
    plan; local dump/restore success does not validate hosted backup operations.
14. **Performance/retention.** EXPLAIN ANALYZE gallery seq pagination on a synthetic
    100/1k/10k-user dataset; member/week and artist/week lookups need their existing
    indexes. Measure p95 latency, lock/pool waits, function invocations, Civitai calls,
    response bytes, bloat/WAL and retention costs. Index presence alone is not a load
    test. Schedule reviewed retention cleanup rather than assuming rate-table TTL.
15. **Go/no-go.** Require complete hosted evidence, measured incident kill delay,
    backup drill, dedicated-account packaged upgrade/rollback, moderation reporting/
    blocking/actor-reason audit, privacy disclosure, operator coverage and budget
    alerts before any public submissions. Otherwise leave the service disabled.
    Release publication, paid resources and public rollout each need separate approval.

No step above was executed by preparing this runbook. For platform differences use
the [Supabase production checklist](https://supabase.com/docs/guides/deployment/going-into-prod).
