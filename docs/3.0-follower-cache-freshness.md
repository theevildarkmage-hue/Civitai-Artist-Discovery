# 3.0.2 follower-cache policy — issue #59

## Root causes and behavior

The profile JSON's numeric count always won over SQLite's independent observation,
even when the JSON entry had no individual fetch timestamp. Existing profiles were
never refreshed by visible-card enrichment, and follower sweeps treated any stored
count as permanently current. These mechanisms explain the incorrect ASH_AI display;
the provenance of the original JSON value is still unknown.

SQLite `creator_followers` is now the authoritative count source for initial Daily
and Time Machine decoration, visible metadata enrichment and follower-based views.
Counts expire after 24 hours. Visible metadata and follower sweeps refresh expired
observations; failed visible lookups are limited to one attempt per creator per five
minutes. An outage retains last-known public counts and metadata. Visible metadata
marks stale fallback counts, and their tooltips qualify the observation.

Two additional timestamp defects were repaired: resolving a followed creator's name
must not renew an existing count's age, and an in-memory completed follower sweep
must not suppress refresh indefinitely. Its unavailable-result grace is five minutes;
successful counts remain governed by their individual observation timestamps.

Counts can legitimately decrease. Fresh lower observations replace higher older
ones; the resolver never chooses a maximum as a repair. Unknown values remain unknown
and are never converted to zero. Booleans, negative/fractional/nonfinite values and
numbers outside SQLite's integer range are rejected. Older timestamped observations
cannot replace newer valid ones. Casefold matching is retained for Unicode names.

## Persistence, I/O and tradeoffs

The existing SQLite row and `fetched_at` column carry count freshness. An additive
NOCASE username index supports ordinary bounded lookups; Unicode casefold fallback
consults only the small public follower metadata table. No artwork/tag scan is needed.
Bulk card decoration loads counts once per page. Count-only refreshes of existing
creators update SQLite without rewriting the large JSON profile cache. Avatar,
unrelated stats and custom profile fields are preserved. New creator profiles still
use the existing JSON persistence path; that path remains a possible future I/O
optimization. No original installation data is a write destination.

During an outage, display and classification use the same last-known numeric count,
with a stale tooltip where metadata enrichment succeeds. They cannot establish an
unavailable current upstream count. Active gallery ordering remains stable under
the existing browsing-session contract; a new load uses corrected stored counts.
The new index is backward compatible and no SQLite user-version increment is needed.
No OAuth, hosted access policy or social-write permission changes are included.

## Verification

Eight new `follower_cache_freshness` tests cover conflicting caches, per-creator
expiry and repeat lookup, decreasing counts and threshold boundaries, invalid/missing
upstream values, offline fallback/backoff, sweep refresh/tag preservation, name-only
resolution age, out-of-order observations and Unicode lookup. Existing read-only
metadata fixtures now provide explicit timestamped follower observations under the
new interface; their original account-isolation and permission assertions remain.

Real validation read only ASH_AI's indexed SQLite row and its profile entry from
the verified backup. The JSON metadata read was throttled to 5 MiB/s with background
I/O priority. An isolated small store reproduced JSON count 8 / SQLite count 2,688;
one real Civitai read returned 2,873 followers for creator ID 12813961 on November 18,
2026. Both initial and visible metadata used 2,873 and classified the creator as
not Emerging. The profile JSON remained byte-identical, and an immediate repeat
made no upstream request. Counts can change after this observation. No full database
was copied or scanned, no source was written, and no social action was sent.

This is real upstream/source validation plus isolated regression coverage. The full
history's packaged acceptance remains pending the startup backfill repair and the
remaining sequential 3.0.2 items. Private receipts retain exact commands and results.
