# Discovery 3.0 Beta owner operations and recovery

This is an operating procedure, not authorization to publish, distribute, invite,
activate collection, change hosted settings or restore over staging. Community
and registry collection remain off until separately approved. The current schema
model is `automatic` (eight immutable migrations); do not replay historical
four/seven-migration bootstraps or reset recommendation quotas.

## Approved ownership and outstanding commitments

The application owner is the initial sole operator, moderator and recovery
approver. Codex is a local administration interface under owner instructions;
it is not a custodian, independently verified moderator, continuous monitor or
on-call replacement. No hosted moderator Auth account is required. Maximum
initial invitation target is five accounts including the owner; exact identities,
distribution and activation still need separate approval.

General privacy/support contact is
[GitHub Issues](https://github.com/theevildarkmage-hue/Civitai-Artist-Discovery/issues).
Never attach tokens, databases, account lists or sensitive incident details.
A private sensitive privacy/security channel remains an owner-approved
**distribution blocker**; see the bundled privacy guide for the proposal.

The approved routine operational log/throttle retention target is 90 days.
Current SQL throttle cleanup is opportunistic after two minutes, not a 90-day
history. Local routine logs have no universal 90-day purge and provider log
retention is outside the application. No retention job or hosted setting is
changed here. Remaining retention, backup custody, budgets and response-time
commitments are proposals pending explicit owner approval.

## Tool boundary and supported actions

Run `scripts/community-owner-admin.py` only through the existing secure project
Credential Manager process launcher. Never put tokens in arguments, chat, SQL,
source, screenshots or plaintext environment files. The local tool verifies the
project/region and postgres authority, refuses redirects, sanitizes failures,
and requires `--execute` plus a nonsecret `--reason`. Mutations are not retried
blindly. The supported administration interface uses Management SQL to invoke
`community_private.owner_admin`; do not assume a Management moderation REST API.
Project-level authority is broad and can bypass workflow audit; its owner actor
label is explicit and is not independently verified per-moderator attribution.
Ordinary clients and runtime service-role credentials cannot use owner_admin.

## Daily operator checklist (proposed cadence)

1. Record UTC time, owner actor `owner-admin:discovery3`, expected revision and the
   exact approved policy. Run the secure read-only health tool with the reviewed
   function revision and a private output path. A new revision needs review.
2. Review reports daily; proposed triage target is 24 hours. Validate artwork and
   verified IDs, hide/remove inappropriate content when approved, resolve/dismiss
   reports with reasons, and record escalation. Do not disclose reporter identity.
3. Review blocks, appeals and invitation expiry/revocation. Registry membership
   never confers Community access. Revocation/block enforcement precedes replay.
4. Check Supabase Dashboard invocation, egress, database usage, errors and 429s;
   check upstream Civitai failures. SQL buckets are neither billed invocations nor
   a DDoS/spend cap. Proposed budgets are 1,000 Community invocations/day and 1,000
   media lookups/day: review at 50/70%, pause at 80%, disable at 90% or any security
   invariant breach. These thresholds require owner approval and manual review.
5. Check dated backup ciphertext hash and successful restore receipt. Proposed
   cadence: daily while testers are active, before approved changes, and weekly
   isolated restore; seven-day retention remains unapproved and unscheduled.
6. Record unresolved incidents and next review. Proposed availability rule:
   disable submissions when the owner cannot cover the next 24 hours. No 24/7
   coverage, measured response SLA or automatic monitoring is promised.

## Outage, disable and credential compromise

An outage leaves Daily Gallery independent and registry registration best-effort.
Stop submission retries, inspect read-only health/catalog/history and provider
status; never reset quotas, broaden grants or restore a database over staging.
For an approved emergency disable, set Community and registry state to disabled
through trusted project management access, then verify current source/revision
and fresh authenticated denial. Secret propagation alone is not proof that every
warm instance changed. Check multiple observed instances and fixed expiry where
applicable; if uncertain, pause distribution and seek project-owner support.
Reopening needs a new owner decision and scoped acceptance.

Suspected credential compromise: owner contains the incident, disables participation
using remaining trusted access if authorized, suspends administration, inventories
affected keys/sessions and approves revocation/rotation. Dashboard account recovery,
Windows Credential Manager recovery and database recovery are separate. Do not
rotate credentials or export raw logs merely to rehearse this checklist. Reverify
source, policies, grants and preserved hashes after recovery.

Private incident record: incident ID, UTC discovery/containment/recovery times,
owner label, affected component/revision, sanitized symptoms, data scope, approved
actions/results, backup digest, notification decision and follow-up owner/date.
The approved routine-log target is 90 days; incident/audit holds need separate
scope and review dates. Do not store raw tokens, IP exports or full member lists.

## Recovery custody and actual recovery scope

Existing ciphertext and restore receipts reside in ignored private local report
folders owned by the application owner; exact locations/hashes belong in the
private inventory, never the public package. The scoped tool captures thirteen
Community/private tables, four sequences, eight migration histories, SQL bodies,
constraints/indexes/triggers and ACL/RLS. Ten checks passed in an independent
loopback PostgreSQL cluster. That is same-account independent-cluster evidence,
not proof of another account, machine or hosted platform recovering successfully.

The archive uses original-account Windows DPAPI. Credential Manager management
access permits a future export while project access survives; it does not decrypt
an existing archive after losing the original account's DPAPI keys. No off-machine
custodian/key escrow is verified. Copying the ciphertext or credential store does
not establish independent recovery.

Prepared drill: owner designates an existing independent account/machine and safe
storage; transfer only a nonsecret canary created by
`scripts/rehearse-recovery-custody.py prepare --directory <new-private-directory>`.
Run `probe` in that second account; it refuses the original account and should
show DPAPI protection denial. This demonstrates the limitation, not portability.
Then separately approve a vetted portable encryption tool, distinct key custody,
synthetic wrong-key/tamper/restore rehearsal and actual scoped encrypted transfer.
Never invent cryptography, put passwords on command lines, export Windows master
keys or leave plaintext dumps. Restore only into a new disposable loopback cluster;
verify all hashes, schema, roles, constraints, histories, sequences and denials;
remove only the owned temporary plaintext/cluster and retain a sanitized receipt.
No test identity is granted hosted administrative access automatically.

Owner is the recovery authorizer. Independent custodian/location, emergency
successor access, RPO24h and proposed one-business-day recovery target remain
unapproved; recovery time is unmeasured until a complete authorized drill. A
DPAPI-only exception must be explicit. Reapply approved deletion obligations
before any restored service is reactivated.

Recoverable today: scoped PostgreSQL data/schema/catalog plus pinned source for
a separately approved compatible Edge redeployment. Not in the archive: Supabase
Auth users/passwords/sessions/provider configuration/signing keys, Edge secret
values/project settings, Storage object bytes, or complete managed-project
recreation. Credentials must be reprovisioned through approved custody, never
embedded in a public manifest. No complete portable or hosted restore is claimed.
The owner reported Free plan; an internal backup flag is not evidence of a usable
retained provider backup. See [Supabase backups](https://supabase.com/docs/guides/platform/backups)
and [DPAPI scope](https://learn.microsoft.com/en-us/windows/win32/seccrypto/example-c-program-using-cryptprotectdata).
