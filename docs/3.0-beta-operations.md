# Private beta operations and conditional staging deployment

Target: `aibelmhucizupzvvhdvf`, us-west-2. Final policy must be disabled.
The master task authorizes staging mutations only after all mandatory gates pass.
This runbook never waives a gate. It does not authorize public activation or a
GitHub push/release.

## Operator architecture

The original database-login provisioner stays unchanged and refuses unsupported
hosted logging controls. The new alternative uses supported Supabase Auth password
authentication and verified TOTP MFA, then the signed JWT through PostgREST.
`community_admin` requires session_user `authenticator`, role `authenticated`,
`aal2`, and an unexpired/unrevoked private auth UUID mapping. Audit attribution
uses that mapped actor ID and `auth:<verified UUID>`; request fields/user metadata
cannot choose the actor. Runtime service_role has no EXECUTE privilege on this
wrapper. Authenticated users can reach the wrapper but are denied inside it unless
all checks pass. EXECUTE is deliberately not described as moderator authority.

The wrapper performs reports/audit, bounded invitations, blocking/moderation,
registry aggregates/deletion/retention under the same transaction lock as writes.
No invitation-management UI exists. Initial enrollment is an independently
authenticated administrative trust action, not signup or self-enrollment.

Before hosted deployment, identify the owner's dedicated staging Supabase Auth
account and verify the supported enrollment/MFA path. No such real operator
account/MFA session has yet been established by this task. Local Auth tables and
claims are fixtures; actual JWT signature/role enforcement is exercised by real
PostgREST, but those tests do not prove hosted Auth enrollment or delivery.

Under the conditional deployment/enrollment scope, create only the dedicated Auth
identity (never a real tester invitation), complete owner-interactive TOTP setup,
and bind its verified UUID to the independently verified owner/operator identity
with a short expiry and audit evidence. No database login password is issued. Do
not put passwords, MFA codes or sessions into SQL, command arguments or reports.
Do not enroll another account or use user-editable metadata as the allowlist.

After enrollment use `scripts/community-auth-operator.py`. Supply only a modern
publishable key via the process environment. The tool privately prompts for the
operator email/password/TOTP, signs in, verifies the single enrolled factor,
executes the restricted RPC and signs out that exact session. Secrets stay in
memory; no browser/app credential storage or management token fallback exists.
Public keys alone are not authority. Ordinary runtime clients cannot moderate.

For a newly approved dedicated Auth identity with no existing factors, the `enroll`
action prompts in a private terminal and serves the enrollment QR only from a
nonce-protected, non-cached ephemeral loopback page. The secret is not written to
a file or printed. Enter the authenticator code back in that terminal. Successful
enrollment returns only the Auth UUID and does not create an operator mapping.
Existing factors are a stop condition; this action never rotates them. Failed
verification attempts clean up only the just-created unverified factor. A forced
process kill can prevent cleanup; inspect that exact dedicated account before
retrying. Transport tests are mocked, so real hosted delivery/enrollment is still
an external acceptance gate, not a demonstrated result.

Rotation uses Supabase Auth's supported password reset/update and MFA recovery
mechanisms under separate approval for any existing hosted credential. Disable
the private mapping first and preserve audit; existing JWTs lose wrapper authority
on the next call because mapping state is checked each time. Re-enroll/reactivate
only after fresh MFA validation and old-session containment. A signed JWT may
otherwise remain cryptographically valid until expiry, so sign-out alone is not
the emergency authorization boundary. Never edit JWT keys for convenience.

Emergency containment: use independently authorized project administration to
revoke the exact allowlist UUID transactionally, record trusted actor/reason and
timestamp, then revoke affected Auth sessions through the supported Auth workflow.
Keep Community disabled. If the management credential is compromised, contain it
through the owner's Supabase access controls under separate rotation approval;
never give it to the application or moderator client. Review audit changes and
restore only through a separately approved compatible recovery path.

## Invitation workflow

The owner supplies each approved username/profile URL. `--profile` is required
for `invite`; it resolves Civitai's fixed-host public user.getCreator and user.getById
and verifies an ID/username round trip. It refuses redirects/foreign URLs,
ambiguous names or changed identities. The resolver never creates an invitation
and is tested with fixtures; no unspecified real account was resolved or invited.

Then the MFA operator uses `invite --profile ... --until <UTC, <=30 days>
--reason ...`. Renewal uses the same bounded action. `invitation_status --target`
returns only that target; `revoke_invite`, `block` and `unblock` are audited.
The database serializes admission and enforces five active accounts total,
including the owner. Registry rows confer no Community rights. Revocation/block
checks precede replay acceptance. Never seed placeholder real identities.

## Verified scoped backup and independent restore

Run `scripts/backup-community-hosted.py` through the existing Windows Credential
Manager launcher, with the reviewed PostgreSQL bin directory and an ignored output
directory. The tool uses only project identity/functions and read-only SQL
endpoints. It exports the actual five Community tables, sequence state, migration
history and function definitions and checks schema/constraints/indexes/triggers,
ownership, all catalog grants/RLS and normalized function bodies against the four
pinned baseline sources in `supabase/deployment-baseline.json`.

It rejects schema drift, encrypts its in-memory archive with Windows account-bound
DPAPI, verifies decryption/integrity and reconstructs roles/schema in a completely
new PostgreSQL cluster. Data, history, sequences, foreign keys, quotas and client
denials are checked there. Original CRLF function definitions are preserved in the
archive; PostgreSQL/psql line-ending normalization and UTC rendering are explicitly
accounted for rather than treating semantically identical timestamps as loss.
It rechecks the hosted snapshot to prove no changes during the verification.
The final runner stops and removes its own checked temporary restore directory.

This is verified scoped application recovery, not a full Supabase platform backup.
It excludes Auth users/sessions/passwords, signing keys, Storage objects and other
managed schemas. The current application does not store media bytes in Supabase.
Future Auth operator recovery needs separate provider account/session/MFA recovery,
and a later deployed-schema export must be reviewed: this baseline-only exporter
fails closed on candidate/release schema. Do not use it after migration seven as
though it captured the new registry/operator tables.

The encrypted artifact depends on the current Windows account's DPAPI recovery
key. Owner approval of backup custody, independent key/account recovery, retention
and RPO/RTO remains necessary before operational activation. Do not email the
archive or write a plaintext key/dump. Full hosted disaster recovery was not run.

The original candidate rehearsal also verifies encrypted dump/restore and rejects
version-10 source against the new schema. After any newer migration, use a pinned
compatible forward fix; never restore version-10 source or broad grants. An
ambiguous migration response requires read-only history/catalog/hash inspection,
not a blind retry, history edit, data reset or destructive rollback.

## Conditional deployment sequence

1. Close every mandatory master-task gate, including actual supported confidential
   operator enrollment, independent encrypted restore and accepted custody. If a
   gate remains unverified, keep this sequence preparation-only.
2. Pin the final clean private commit and generate the `--schema-model release`
   manifest. It includes the four immutable baseline files and migrations five,
   six (application registry), seven (Auth operator/access states), both Edge files
   and the exact transaction hash. Original pinned migration five is unchanged.
3. Repeat identity/region, secure project-scoped authority, writable SQL identity,
   exact hosted function source/version, four history entries, disabled/ratings
   digests and historical hashes. Check supported Auth objects and restricted
   NOLOGIN community_operator prerequisite. Do not require account-profile access.
4. With gates passed, apply only migrations five–seven and history in the prepared
   single transaction. The bundle checks preservation before commit and stops on
   already-present/private schema or history/owner mismatch. It does not bootstrap
   the original four migrations again. Rehearse exact interruption/retry first.
5. Deploy only the compatible pinned community-v1 entry point, preserving its
   opaque Civitai credential transport/JWT gateway configuration. Keep Community
   disabled, ratings 1,2 and registry disabled. Record the actual returned revision;
   never assume its number. Compare deployed source and schema fingerprints.
6. Perform release-model catalog, actual public/ordinary authenticated denials,
   fresh authorized owner Civitai login and MFA operator checks. No historical
   recommendation modification or quota reset is allowed. Disposable owner-only
   writes need an explicit bounded window and clean up only those exact fixtures.
7. Close the window and return disabled, then verify policy through the hosted
   handler and compare historical hashes. If fresh identity/operator/gate evidence
   is missing, do not claim hosted acceptance or proceed to public beta.

## Monitoring and five-person daily checklist

The production entry point uses a shared PostgreSQL `project:community` bucket:
30 admitted requests/minute across instances, in addition to token/member and
per-instance ingress/concurrency bounds. Rejected increments roll back, so the DB
counter is admitted calls, not all attempted requests. Two actual local Deno
instances are tested against the same PostgreSQL bucket. The global budget can be
exhausted by hostile token attempts, trading availability for bounded upstream
amplification; it is not a DDoS gateway or a billing cap. At most three due artworks
with two media checks each are processed per gallery request. Worst-case admitted
gallery load is 180 media lookups plus 30 UserInfo requests/minute before leases
and eligibility caching; Daily Gallery's separate traffic is not included.

Before activation the owner names an on-call operator and approves absolute daily
invocation/egress/Civitai budgets. Proposed initial limits: 1,000 Community
invocations/day and 1,000 upstream media requests/day; alert at 50%/70%, stop the
test at 80% and emergency-disable at 90% or any invariant breach. These are proposed
operational limits, not automatically enforced billing guarantees. Free-plan
invocation/egress exhaustion remains possible; 429 responses still consume Edge
invocations. Do not describe local counters as provider measurements.

Daily: confirm disabled or the separately approved bounded window; run the secure
read-only health tool with the expected function revision; check quota/audit
invariants, API/5xx/429 rates and provider Usage in the dashboard; inspect aggregate
registry_stats/reports with MFA; review invitations/expiry and moderation coverage;
verify encrypted backup freshness and recovery custody; record budget usage and
any incident. Do not export raw tokens, member lists or IP logs into reports.
The health tool only reads sanitized Community aggregates and policy digests and
does not enumerate the registry or call Civitai. It is not a substitute for MFA
moderation authorization or real provider cost metrics.

Before a hosted test, observe at least three distinct warm/cold function instances
and 30 bounded requests with redacted execution identifiers; require disable,
invitation/block revocation and operator disable on every observed instance within
30 seconds. No client loop alone proves multi-instance propagation. Stop on any
accepted operation after the deadline. Alert on >1% 5xx for five minutes, any audit/
quota invariant breach, unexpected spend, sustained upstream 429 or stale review
backlogs. These hosted timing/traffic measurements remain unexecuted until the
gates and authorized identities are available.
