# Community ledger security and staging preparation

Prepared 2026-10-22. Local hardening only; no hosted migration/function/configuration
change, publication or real recommendation write is authorized here.

## Trust boundary and findings

Public clients call the controlled Edge handler using Civitai OAuth. The desktop
backend is a distributed client and has no authority to hold a privileged Community
credential. Fresh fixed-host UserInfo determines stable member identity; independent
artwork lookups determine uploader. Client member/uploader fields are rejected.
Supabase Auth JWTs and Civitai opaque access tokens are different credentials.

No public-role ledger-write bypass was found in the local adversarial executions.
A replay gap was found: an existing request key/image could return success despite
changed uploader or invalid display-name input. That path did not add records or
consume quota, but accepted an invalid canonical request. Additive migration
202610220001 validates all inputs before lookup and binds replay to member, image
and persisted uploader. Display-name changes remain allowed because UserInfo names
can change without changing the verified member or artwork. Reusing a key for a
different image/uploader is rejected. Identical retries return the original result.

The existing SQL quotas serialize member, artist and image locks and count all
accepted recommendations, including withdrawn/hidden/removed entries. No refund
or client-supplied week is accepted. Monday 00:00 UTC determines the stored week.
The global image unique constraint forbids duplicate artworks, including races.

The handler now prefers the platform-injected SUPABASE_SECRET_KEYS default entry,
sent in apikey only. A malformed dictionary fails closed instead of silently
switching credentials. An absent dictionary permits the legacy injected service-
role bearer/apikey contract for existing local infrastructure. Neither credential
is returned to the desktop. Modern keys still map to privileged service_role; this
is the supported API path, not a claim of a narrowly restricted database principal.
See [Supabase key transport](https://supabase.com/docs/guides/getting-started/api-keys)
and [injected variables](https://supabase.com/docs/guides/functions/secrets).

## Object privilege matrix

All five tables: community_members, community_recommendations, community_audit,
community_rate_buckets, community_submission_requests. All have RLS enabled,
FORCE RLS false, and no ordinary-client policies. There are no Community views.

| Role | Table SELECT/INSERT/UPDATE/DELETE/TRUNCATE | Sequence SELECT/USAGE/UPDATE | RPC EXECUTE | Expected access |
|---|---|---|---|---|
| anon | Denied on every table | Denied on both | Denied on every RPC | None, even with public API key |
| authenticated | Denied on every table | Denied on both | Denied on every RPC | No direct ledger/operational access |
| service_role | Denied on every table | Denied on both | Allowed on seven intended RPCs | Controlled server only |
| Owner/migration operator | Administrative authority | Administrative authority | Owner authority | Schema migration/recovery, outside user authorization |
| authenticator | Gateway login; must not receive ledger grants | No intended grants | Role switch only | Assumes verified gateway role, not a member identity |

The local HTTP fixture uses cad3_rest as its NOINHERIT gateway login, with membership
in anon/authenticated/service_role so PostgREST can select the verified request role.
Its ephemeral database password is held only in process environment. Like hosted
authenticator, this is a trusted gateway credential, not a distributed-client role.
The read-only audit role is not an application handler role and must never be used
to serve clients; its catalog visibility does not establish ordinary-user access.

Both sequences are community_recommendations_seq_seq and community_audit_seq_seq.
All tables/sequences/RPCs are owned by the migration executor: cad3_admin in owned
native tests; postgres is the required hosted migration owner. All seven RPCs are
SECURITY DEFINER with fixed public,pg_temp search path:

| RPC | Purpose / mutation |
|---|---|
| community_quota | Per-member current UTC-week count; reads ledger |
| community_gallery | Bounded cursor page/public attribution; reads ledger |
| community_take_rate | Digest/member throttle and cleanup; operational writes |
| community_submit | Ownership inequality/quota/unique checks, preview or atomic recommendation+audit |
| community_submit_once | Atomic replay lookup/delegation and request-key persistence |
| community_withdraw | Verified member's own recommendation status plus audit |
| community_moderate | Privileged hide/remove plus audit; no public handler operation |

Owner access, SECURITY DEFINER execution and BYPASSRLS are deliberate trusted
boundaries. RLS is not protection from an administrator, table owner or stolen
privileged credential. service_role cannot SET ROLE from anon/authenticated, but a
stolen service credential can call delegated RPCs directly and impersonate member
arguments, bypassing Edge authentication/policy. It may also reach other project
objects allowed to that role. Keep it solely in the controlled service. No claim
is made that quotas or RLS contain arbitrary owner-level SQL.

The native inventory records every table, sequence and RPC separately with actual
owner, RLS/forced flags, role access and search path. `supabase/tests/security_inventory.sql`
provides the same read-only catalog query for hosted verification. The staging
audit found schema owner pg_database_owner, database owner postgres, automatic RLS,
and creator-specific grants including TRUNCATE; final explicit revokes are mandatory.

## Policy and failure behavior

Canonical server states are disabled, read_only and enabled. Only enabled permits
recommendation/withdrawal/verification operations. Missing/unknown state fails closed;
read_only permits browsing. Client flags cannot grant permission. The remote policy
does not limit a stolen service credential or owner, and already committed requests
cannot be undone by a toggle. Revoke BOTH submit and submit_once RPC grants during
an emergency while investigating secret propagation. Hosted propagation remains
unverified. No automatic offline recommendation queue is introduced.

Expired/revoked/ambiguous UserInfo, mismatched IDs, incomplete artwork/owner metadata,
upstream outages and unacceptable ratings fail before acceptance. Shared failures do
not change personal galleries. A local HTTP test commits then suppresses the success
representation; explicit same-key retry returns replay with no additional audit or
quota slot. That fault injection lives only in supabase/tests/local_service.ts.

## Exact data inventory and minimization

| Table | Stored fields | Classification / reason |
|---|---|---|
| community_members | civitai_id, username | Public Civitai stable identity/name, retained for attribution; personal data despite being public |
| community_recommendations | seq, image_id, creator_id, member_id, submitted_at, week, status | Image/uploader identifiers are public metadata; the member/artwork association, time, status and chronology are app-generated activity used for quotas/feed |
| community_audit | seq, image_id, action, at | App-generated acceptance/withdrawal/moderation activity and UTC time |
| community_rate_buckets | key, started_at, requests | Token SHA-256 digest or stable member-based key, time and request count; pseudonymous identifying activity, not anonymous data |
| community_submission_requests | member_id, request_key, image_id | App-generated replay identifier bound to stable member and accepted image |

No field stores IP addresses, email, OAuth access/refresh token values, device IDs,
image bytes, prompts, full Civitai profiles or service/database credentials. The Edge
ingress limiter temporarily holds runtime peer IP in process memory; this is not a
database column. Gateway/operator logs may independently retain IP metadata and need
their own privacy/retention review. A token digest is user-associated metadata and
must not be described as a raw token or as nonpersonal data.

Keep stable numeric IDs for ownership/quota correctness. Usernames are the only
mutable public identity presentation copied into the ledger; replace with on-demand
display lookup only after a separate design review of availability/caching costs.
Do not remove identity/replay/audit fields destructively. No field or row was removed
in this milestone. Recommended next work: bounded rate cleanup schedule, defined
audit/replay retention and deletion process, public attribution disclosure, and
moderator actor/reason auditing. Retention cleanup is not currently implemented;
rate-bucket cleanup is traffic-driven and accepted records/replay keys accumulate.

## Verification boundaries and deployment

Local coverage uses native PG17.11 with real low-privilege sessions, real Deno and
PostgREST, and synthetic explicitly isolated identities. The removable Lab uses
public metadata snapshots/decoded artwork with simulated sessions, never actual
creator credentials. This does not establish live OAuth consent/revocation semantics.
The runner now feeds initdb's prompt from an anonymous pipe; new Lab capability files
use Windows DPAPI. Existing interactive profiles/registrations are not rewritten.
No plaintext credential file is created by the new runner/Lab path.

The current management token is unavailable in the process and previously authorized
location. No unrelated credential search or raw-key retrieval was performed. The
previous audit is historical hosted evidence; actual modern-key injection/PostgREST
mapping is still a blocker requiring authorized hosted validation. No hosted change
is justified merely by local test success.

Use the [staging runbook](3.0-staging-runbook.md) after explicit approval, with all
four pinned migrations and state disabled. The prepared hosted verifier checks catalog
denials and optionally bounded table GET/invalid RPC requests; it sends no valid
recommendation and never invokes the handler. It has not been executed hosted.
Broader hosted CRUD denial probes need an approved disposable transaction/rollback.
Public rollout additionally requires report intake, submitter blocks, moderator
actor/reason audit, rating drift revalidation, recovery/monitoring and privacy review.
