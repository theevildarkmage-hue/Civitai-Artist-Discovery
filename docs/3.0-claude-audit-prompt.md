# Independent Discovery 3.0 audit prompt

Copy everything below into Claude Code with this repository open. Read
`docs/3.0-claude-audit-access.md` first. Use current source and current hosted
evidence; do not assume a candidate migration has been deployed.

---

You are performing an independent adversarial audit of Civitai Discovery 3.0 Beta.
Your job is to find reproducible application defects, security problems, unnecessary
complexity and measured performance bottlenecks. Treat previous reports as claims
to verify, including claims written by Codex. Follow AGENTS.md.

Scope: the current private `3.0` worktree, the sanitized `development/3.0` publication
history, the built Windows candidate when available, and read-only Supabase staging
`aibelmhucizupzvvhdvf`. Record exact commits, dirty status, package provenance and
actual hosted function/migration versions before drawing conclusions. Distinguish
reviewed local candidates from deployed behavior.

Boundaries:

- Audit and report; do not apply fixes, commit, push, publish, deploy, migrate,
  change policy, create accounts/invitations/recommendations, reset quotas or
  modify existing application profiles/databases/OAuth sessions.
- Do not obtain, print or export credentials. For hosted evidence, invoke only
  `python -B scripts/community-audit-readonly.py --output reports/claude-review/hosted.json`,
  or use the separately authorized exact-project, read-only Supabase MCP connection.
  Do not modify/bypass that helper, use the general secure launcher with arbitrary
  commands, read Windows Credential Manager directly, inspect token files, or run
  owner-admin/deployment scripts. Verify effective read-only authority first.
- Inspect only Community schema/catalog/indexes/function definitions and aggregate
  counts/statistics. Do not enumerate registry identities, invitations, Auth users,
  reports, audit payloads, request bodies, secrets, or operational logs. No hosted
  flood/load tests, arbitrary privileged RPC execution, DDL, DML, or EXPLAIN ANALYZE
  on mutation functions. If access is insufficient, report the exact gap.
- Use owned disposable local fixtures for mutation, concurrency, outage and denial
  tests. Never borrow a real user's OAuth credentials or treat a fixture identity
  as proof of successful real Civitai authentication. Linux execution is waived.

Review priorities:

1. Authentication and authorization: the normal local Civitai grant versus the
   independent read-only Community grant; actual server-side UserInfo and scope
   verification; expiry/revocation; redirect/body/response bounds; no privileged
   token transport to clients. Prove that invalid credentials cannot create SQL
   throttle buckets, and that denial caching never accepts stale positive identity
   or turns an upstream outage into a long authentication lockout. Evaluate the
   remaining random-token provider-cost limit honestly.
2. Hosted access: effective RLS, table/column/sequence/schema grants, every public
   SECURITY DEFINER routine, owner-only administration and owner audit labels.
   Check search paths and callable legacy routines. Verify metadata instead of
   assuming a function's presence implies it is executable. Normal users must not
   enumerate protected data or invoke privileged RPCs directly.
3. Community correctness: personal quota exception only for verified owner
   11107642; everyone else three/week; owner still shares the three-per-artist cap.
   Check atomic races, duplicate/self/replay protection, invitations, blocks,
   expired invitations, policy propagation and emergency disable. No new consent
   system, moderator account or application-side authorization bypass is wanted.
4. Gallery expiry and pagination: reproduce at least 60 expired synthetic rows.
   Check raw-window cursor advancement, deduplication, warm versus cold page sizes,
   deleted/rerated/private art, lease races, transient failures, fairness and
   truthful end-of-list/pending states. A viewer-specific detail failure must not
   globally quarantine artwork or block the next eligible reviewer. Shared
   positive review must retain independent public visibility/rating proof and
   authenticated numeric ownership/public-flag verification. Do not suggest
   serving stale ratings/deleted artwork or unbounded provider fan-out.
5. Ratings UX: reproduce rapid, arbitrary-order combinations in both rating panels
   on desktop and mobile. Delay POST replies and gallery reads. Click again while
   a save and while a reload are in flight. Check optimistic state, serialized
   latest-intent persistence, no stale overwrite, one final reload per settled
   burst, rollback/re-read after failures, at least one selected rating and
   cross-window content-control propagation. Check that stale restricted artwork
   cannot remain visible while a narrower selection is saving.
6. New recommendation notices: background work must not move scroll position,
   mutate foreground cursors, double-count IDs or resurrect an aborted notice.
   Verify hidden-tab behavior, bursts above the scan bound, content filtering,
   error recovery and newest-first explicit refresh.
7. Local data correctness: cursor cycles and empty pages; incomplete sync/resume;
   suspicious-snapshot preservation versus legitimate removal; same-block capture
   reservation/rebuild races; retry locks, shared pacing and 429 cooldowns;
   cancellation; busy recovery polling; transactional settings. Prove preservation
   with temporary SQLite record hashes, not just mocks.
8. Calendar: new builds consistently use America/Chicago on PCs/browser contexts
   in different timezones, including 23/25-hour DST days. Stored historical ranges
   and checkpoints must not be silently reinterpreted or replaced on a conflict.
9. Repository/code cleanup: unreachable routes and settings, duplicated state and
   parsing, stale docs/tests, misleading comments, swallowed exceptions, accidental
   coupling, encoding defects, generated/runtime files and obsolete experiments.
   Propose a concrete scoped cleanup; do not rewrite everything or delete profile
   snapshots, recovery artifacts, reports or history as incidental tidying.
10. Performance: measure request counts/latency, repeated metadata fetching,
    stale-cache behavior, bounded thumbnail/lock retention, SQL indexes/query
    plans, request serialization, startup, gallery rendering/infinite scroll,
    detail metadata, video and DOM/listener churn. State dataset/device/method,
    compare a baseline where feasible, and separate measured gains from guesses.
11. Distribution: inspect the actual frozen package, production fixture isolation,
    dependency provenance, beta/stable update separation, hashes, rollback and
    Windows file locks. Independent signing is intentionally deferred by the
    owner; assess the documented trust limitation and proposed rollout, without
    inventing a key or turning it into an unapproved release gate.

12. LAN parity: the owner explicitly requested the 2.2.1 direct-IP model, without
    pairing, secret links or extra accounts. Verify the toggle/restart flow,
    main-adapter address selection, disabled binding and Host/Origin guards.
    LAN deliberately shares this PC's signed-in app with reachable devices;
    do not claim LAN client isolation or per-device identity. Community must
    still verify Civitai identity, scope, invitations and quotas. Verify defaults
    fill missing preferences and preserve explicit off/coverage choices.

Run applicable existing tests through `scripts/run_tests.py` using isolated data;
native PostgreSQL/Edge tests require their documented owned-cluster runner. Preserve
failed-run diagnostics and investigate failures. A passing mocked test is not
proof of live hosted behavior. Do not rerun unrelated broad suites merely to
inflate counts; describe exact coverage and gaps.

Deliver a senior-engineer review with findings first, ranked Critical/High/Medium/Low.
For every finding provide file:line or hosted catalog evidence, failure mechanism,
affected user flow, safe reproduction, impact, confidence, and a minimal proposed
fix with regression coverage. Identify false positives from prior audits explicitly.
Separate confirmed bugs, unresolved hypotheses, accepted owner decisions and
optional cleanup/performance ideas. Explain existing safeguards and compatibility
tradeoffs. Finish with exact tests run/pass/fail/skip, data-preservation evidence,
remaining access gaps, and a prioritized remediation plan. Do not claim the repo
is clean, secure, fast or production-ready without supporting evidence.
