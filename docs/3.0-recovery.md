# Community recovery and health

The maintained entry point is `scripts/community-recovery.py`. It provides health,
encrypted export, archive validation, restore into an owned disposable PostgreSQL
cluster, and clean bootstrap validation. The old `backup-community-hosted.py` and
`community-health-readonly.py` command lines are retired; their historical import
helpers/tests and dated receipts are retained for compatibility. The old
`discovery/community_catalog.py` models are not the current operational gate.

## Supported scope and custody

The development manifest `supabase/recovery/development-v16.json` pins all sixteen
source migrations, seventeen application tables, four sequences, schema constraints,
indexes/triggers, and full routine/role/grant/RLS inventory. Additional objects,
changed definitions or grants, altered history, and missing tables fail closed.
Do not update a count or digest merely to accept unexpected hosted drift. Review
the next migration and rerun clean bootstrap/security/restore tests before changing
a versioned manifest. Do not overwrite historical manifests or encrypted archives.

Archives are protected by Windows user-account DPAPI, with integrity verification;
there is no plaintext or insecure cross-platform fallback. Recovery still depends
on that Windows account's keys. This is not demonstrated cross-account disaster
recovery. Preserve the Windows recovery/custody arrangements separately.

Scope is Community application rows (including identity/device hashes), schema,
migration history, sequences, functions and security permissions. It excludes
Supabase Auth configuration/users, Storage object bytes, secret values, platform
settings, billing and a complete Edge deployment backup. Do not call it a complete
hosted backup. Logs/reports contain aggregate counts and digests, never exported rows.
The bounded response/archive limit is 32 MB; exceeding it stops rather than making
a partial backup. Review a larger, equivalently protected transport if growth
requires it; do not silently omit rows.

## Commands

Use the existing secure owner-management credential workflow. An explicitly set
`SUPABASE_ACCESS_TOKEN` supplies authorization privately. Development may fall back
to the reviewed Development Windows Credential Manager helper. Production hosted
health/export requires an explicit `SUPABASE_ACCESS_TOKEN` injected by the private
Production credential workflow; it never falls back to the Development store.
The operator must select the independently scoped Production credential, not
reinject the broad Development token. Local bootstrap/archive verification needs
no management token. Do not paste keys into chat, git, scripts or CLI arguments.
The default reference is bound to the existing Development project. A Production
manifest is unbound until provisioning; it always requires an explicit project
reference for export and archive verification. The management transport accepts
read-only project/catalog/secret-digest GETs and the read-only SQL endpoint only;
it cannot deploy, migrate, change keys or write hosted records.

```powershell
$recoveryBins = "$env:LOCALAPPDATA/CAD3Tools/postgresql-17.11-5/pgsql/bin"
python scripts/community-recovery.py health --expected-function-version 33 --expected-access-mode invite_only --output reports/health-new
python scripts/community-recovery.py backup --bin $recoveryBins --expected-function-version 33 --output reports/backup-new
python scripts/community-recovery.py verify --archive reports/backup-new/community.dpapi --bin $recoveryBins --output reports/restore-new
python scripts/community-recovery.py bootstrap --manifest supabase/production/bootstrap-v1.json --bin $recoveryBins --output reports/production-bootstrap-new
```

Choose a fresh output directory each time. Backup is successful only when its
`verification.json` includes a passing real restore receipt. It decrypts in memory,
creates a fresh loopback-only SCRAM PostgreSQL cluster with a random password and
current-account directory ACL, reconstructs from pinned repository migrations,
restores rows/history/sequences, and compares the full snapshot/security inventory.
Native child processes discard every inherited `PG*`, `SUPABASE*`, `CAD*` and
`CIVITAI*` variable before setting their owned connection values. This prevents
libpq service/host-address overrides and keeps hosted/application credentials out
of restore processes. The owned SQL sessions explicitly enforce
`standard_conforming_strings=on` for literal-safe restore statements.
Archive definition/history strings are never executed as SQL. The cluster is
stopped and its plaintext directory removed afterward. Existing profiles, databases,
installations and hosted projects are never restore targets of this tool.

For policy-specific health checks also pass `--expected-community-state` and
`--expected-registry-state`; only their hashed provider values are compared. These
are explicit expectations, not an inference from an old report. Development health
defaults to expecting invitation-only access; an owner-approved future public-mode
check must select that expectation explicitly. Function revision is pinned by the
caller, independently of the migration schema version. No invocation-cost or actual
upstream uptime measurement is claimed by these structural checks.

## Tests and operational use

`python tests/current_recovery.py` exercises pinned manifests, source/path drift,
real owned Production bootstrap, public quotas, duplicate/self/artist caps, client
and admin denial, RLS/grant/body tampering, encrypted restore and adversarial archives.
Native checks use `CAD_POSTGRES_BIN` or the installed CAD3Tools PostgreSQL directory;
they skip explicitly if unavailable. Windows DPAPI cases skip on other platforms.
Available native checks must pass before a schema promotion; a skip is not a pass.
Run existing PostgreSQL/Edge authentication and submission suites as well when
changing server/security behavior; recovery tests do not replace real HTTP tests.

The owner is responsible for periodic backups, fresh restore receipts, retention,
custody and incident records. A live restore or rollback requires its own reviewed,
approved project-specific operation; this tool deliberately cannot overwrite an
existing database URL. Preserve audit/replay/quota history. Before an incident
restore, inspect legitimate writes made since the backup and plan reconciliation.
Issue #10's technical consolidation can be assessed against this maintained path;
closing a GitHub issue is a separate owner action, not performed by these commands.
