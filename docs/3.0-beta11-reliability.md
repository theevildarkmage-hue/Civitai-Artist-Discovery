# Beta 11 local reliability candidate

Baseline: validated private Beta 10 source `22c2f5529c9579c483757a44f3c680b52f20d287`;
published sanitized source `df58f53a03368f25db61c0b9f43c5db1be51fe7c`.
Local work only. Beta 10 assets/backend and existing installations are unchanged.
See [the complete audit tracker](3.0-audit-tracker.md).

## H-01: protected credential persistence

Credential reads, encrypted writes and deletion share a reentrant file lock.
Lock order is primary refresh then file; file access never acquires refresh.
Cloud renewal holds its independent single-flight lock during network work and
briefly acquires primary refresh/file locks only to merge and save.
Ordinary file reads do not wait for provider I/O.

Writes use a unique temporary file containing ciphertext only, flush/fsync, atomic
replace and seven attempts over at most about 0.8 seconds of sharing-delay sleeps.
Temporary files are cleaned up. Profile layout, DPAPI/Secret Service and plaintext
rejection are unchanged. JSON profile/follow/candidate cache readers now share the
same locks as their writers; read-modify-write transaction semantics are unchanged.

If a remote rotation succeeds but secure persistence fails permanently, keep the
new grant in process memory, retain the old on-disk file and report temporary
storage unavailability. A later read retries the protected save no more often than
every fifteen seconds. Refuse another provider rotation until the pending grant
is durable; never redeem the invalidated older on-disk credential again in that
process. Status exposes only a persistence-pending boolean, not credential values.

This is **not crash/disk-failure recovery**: a crash, forced exit or power loss
before the new grant becomes durable can still require fresh authorization.
The application already claims a single instance per data profile. File locks
coordinate its threads; bounded replace retry tolerates unrelated external readers.
Independent processes deliberately bypassing single-instance protection cannot
safely redeem the same rotating provider grant and are not claimed supported.
Different profile directories remain isolated; no stable/beta store migration.

Tests use synthetic credentials, temporary real Windows DPAPI files, a real sharing
lock, mocked provider rotation and a separate-process protected-store reopen.
No real user credentials or stable installation are accessed.

## M-03: safe diagnostics

Unexpected Community failures now produce fixed operation/category identifiers
and a random correlation ID, never exception strings, type names, request fields,
headers, URLs, causes or tracebacks. Browser responses retain the generic error
and expose only that correlation ID. The existing rotated local log remains bounded.
Repeated operation/category failures coalesce for sixty seconds; the diagnostic
deduplication map is bounded to 64 entries. Outage spam cannot grow an unbounded map.
Synthetic exception-message, dynamic-class-name, URL, header and nested-cause
canaries were absent from both actual handler responses and written logs.

## M-01: enrollment state and targeted recovery

Authentication status now distinguishes ready, silently renewable, temporarily
unavailable, incomplete enrollment, and expired/revoked device authorization.
Only fixed reasons and recovery actions reach the browser. Incomplete enrollment
survives a protected-store reload; custom clients are identified as unsupported
for the existing built-in Community audience, without weakening audience checks.

An explicit Reconnect Community action obtains a new nonce-bound assertion through
the existing interactive Civitai flow. It rejects account/client changes before
replacing credentials. Challenge outages do not launch a browser or erase Daily
credentials. If the provider issues a new same-account primary grant but Community
exchange fails, preserve that new verified grant: the provider may have superseded
the old one. Signed assertions are consumed and never persisted. No Civitai API or
refresh token is sent to Supabase. No hosted protocol changes are required.

Existing device renewal remains silent; missing/expired initial identity proofs
cannot be recreated through refresh and require fresh authorization. An actual
Community authorization rejection expires only the matching local Discovery
session so its next request can renew; revoked renewal families still require
fresh authorization. Daily remains connected throughout simulated Community outages.
The existing Daily-token prerequisite (M-06) is tracked separately, not redesigned.

Tests use simulated challenge/exchange/provider responses and actual browser UI on
desktop/mobile. They do not establish new real-provider or hosted acceptance.

## M-04: bounded local gallery hydration

Cold pages previously verified artworks sequentially, with three provider calls
per artwork. Concurrent browser requests duplicated that work; expired cache rows
were rendered while background revalidation ran. Gallery pages now reuse the
existing globally bounded three-worker metadata admission, coalesce pending keys,
and pace artwork starts at least 100 ms apart across requests. There is no waiting
worker queue or new executor. Failed keys retain the existing sixty-second retry
backoff. This is not a provider-wide rate limiter; other API paths remain unchanged.

Gallery hydration waits at most four seconds for metadata progress, then returns
the existing retryable unavailable error. Completed metadata remains cached for
retry. A failed page does not return a partial page or advance its cursor. Warm
pages perform no upstream metadata calls. An expired or unavailable cache row is
not rendered by this gallery path; ownership, current verified rating, hidden
artwork/tag/user and blocked-user checks still run before browser serialization.
Submission verification and hosted admission are unchanged. Other non-gallery
cache consumers retain their existing freshness behavior.

Controlled measurements (real verifier parsing and SQLite, synthetic transport):
24 mixed image/video items at 60 ms per upstream call took 4.56 s before, 2.84 s
after pacing; warm 0.011 s / 0.010 s with zero additional metadata calls. Four cold
concurrent requests fell from 288 calls to 72, 4.57 s to 2.61 s. Twelve expired plus
twelve cold items with two unavailable entries now returned 22 current items
instead of rendering 24 including stale unavailable metadata (2.32 s before /
2.67 s after; the new path performs the previously skipped checks). Six cold items at
180 ms/call took 3.29 s before / 1.35 s after. A blocked verifier returned
UNAVAILABLE at 4.00 s and retained progress for a successful retry.

These are local controlled latency measurements, not live Civitai/browser timeout
observations. All measured calls were below the existing sixty-second browser
budget; no claim is made that arbitrary provider delays can yield a successful
page in that time. Backend admission/profile work and SQLite/filesystem delays
are outside the four-second hydration wait. Extreme slowness returns a retryable
failure; the UI does not silently drop rows. Freshness is the existing 24-hour TTL,
not real-time upstream deletion/rating detection. No hosted changes are required.

## Independent-review corrections

Review of c5286e3 found that forced retries restarted completed verification.
The browser now assigns one opaque UUID to each intentional Refresh action and
retains it only through retries of that first-page operation. Ordinary loads,
content-control invalidation, account changes and observed OAuth completion clear
it. It is a work identifier, not an authorization credential.

The local cache binds each identifier to the server-observed account and immutable
content profile. The server assigns the verification watermark; clients cannot
supply a timestamp or mark an artwork verified. Only successful, still-fresh,
available metadata at or after that watermark counts toward the operation.
Backend admission and viewer filtering still execute on every attempt. The
identifier is stripped before any hosted request. No schema or hosted change.

Contexts are per cache/profile, capped at 64 and expire after 120 seconds without
extension. Cleanup is lazy on access. Unknown, expired or evicted UUIDs begin a
fresh boundary; malformed IDs and incompatible account/control reuse are rejected.
Legacy forced calls without an identifier remain individual fresh operations.
No browser automatic-retry loop was added. Cancellation prevents stale UI updates;
an already running HTTP hydration may finish its existing four-second wait and
up to three admitted workers, but has no continuing replacement loop.

At 200 ms/provider call, the original forced attempts each returned UNAVAILABLE
at four seconds and consumed 63 calls including background work. Corrected
24-item operations use 72 calls total across an initial unavailable response and
a successful retry; a second intentional Refresh performs another fresh 72 calls.
Actual local HTTP/Chromium tests exercise this path, while upstream transport and
authentication remain synthetic. Cache expiry remains the existing 24-hour policy;
this is not a promise of real-time upstream deletion detection.

Legacy custom-client profiles now derive unsupported capability directly from
the configured client, independent of stored enrollment metadata. Daily stays
connected; Community explains the built-in-client requirement and hides Reconnect.
The direct reconnect endpoint returns fixed UNSUPPORTED_CLIENT / HTTP 409 before
launching authorization. No client switch, credential deletion or revocation is
performed. A manual switch requires fresh authorization and retains the existing
client-switch semantics; it is not performed by this correction.
