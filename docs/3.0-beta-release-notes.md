# Civitai Discovery 3.0 Beta — Windows prerelease notes

## Beta authenticated activity notice

Discovery 3.0 Beta automatically records your verified Civitai account ID, public
username, first-seen and last-seen timestamps, app version, and platform in its
private Supabase registry after server-side identity verification. Authentication uses a signed identity proof and a Discovery-only session, keeping user
Civitai API access and refresh tokens local. This supports
beta usage and compatibility monitoring. Activity updates occur at most once every
12 hours. The registry stores no OAuth tokens or browsing history, is not publicly
searchable, and does not grant Community access. To request deletion, contact the
maintainer through [GitHub Issues](https://github.com/theevildarkmage-hue/Civitai-Artist-Discovery/issues)
for general support. Do not post tokens, account details or sensitive deletion/security
requests publicly. A private channel requires owner approval before tester distribution.
Later authenticated use can recreate a deleted registry entry.


## 3.0.0-beta.11 - Shared Community Gallery pipeline

- Community now uses the same local artwork metadata, hidden-tag checks, Content
  Controls, caching, thumbnails, video presentation and card rendering as Daily Gallery.
- Supabase supplies accepted recommendation IDs and attribution, up to 50 per page;
  gallery reads no longer trigger external artwork verification or three-record cold pages.
- Seven-day expiration, moderation, invitation checks and submission quotas remain
  server-side. Community is invitation-only, not generally available.
- Civitai API credentials remain local; Community uses Discovery-only authorization.
- Recover a missing Community session with Reconnect Community, without discarding
  the Daily login. Local credential writes tolerate bounded Windows file contention.
- The matching staging backend is community-v1 v33, with 14 applied migrations.
  Legacy Beta 10 requests that omit a page size retain a 24-record default.
- Existing beta users: Settings -> Application updates -> Check now, then download
  and install the beta update. Close duplicate old app instances before reopening.
  Preserve the portable data folder; do not extract over a running installation.
- Windows portable prerelease; unsigned executable may trigger SmartScreen. Stable
  2.2.1 stays on its own update channel. Linux application acceptance was waived.
- Actual owner desktop/mobile acceptance returned 13 recommendations as 12 artist
  cards. Larger pagination and failure scenarios used controlled fixtures, not hosted
  test recommendations. No universal provider-latency or media-availability guarantee.

## 3.0.0-beta.6 - Community update notices and local reliability

- While Community is visible, check for new recommendations once per minute.
  A centered notice reports the count; use Refresh to show the newest at the top.
  Background checks do not replace cards, change pagination, or move your place.
  Checks pause on hidden tabs. Large bursts show an honest bounded count such as
  `96+`; transient failures preserve the existing gallery and notice.
- Ignore unsolicited OAuth callbacks with a wrong or missing state, keeping the
  legitimate login pending. Reject duplicate callbacks without replacing its result.
- Restore the complete previous preference file if applying a content filter fails.
- Bound the in-memory gallery ordering cache to 64 recently used views. Evicted
  views recalculate on next use; no profile or archive data is deleted.
- Route collection, auto-capture and startup errors through redacted rotating logs.
- Recovery verification now distinguishes live operational throttle-counter changes
  from protected-data changes. The captured throttle records must still restore
  exactly. The owner quota exception is recognized when checking restored quotas.
- Community remains invitation-only. This patch does not change hosted functions,
  grants, registry settings, invitations, recommendations, or quotas.

## 3.0.0-beta.5 - Audit security fixes and owner testing

- The verified application owner has no personal weekly recommendation limit
  for testing. Everyone else retains three per week. The shared three-per-artist
  cap, invitations, blocks, duplicate/self protections and audit history remain.
  The new UI labels this owner-only exception explicitly; no user can enable it
  through application settings or request fields.

- Reject Windows UNC, drive/ADS, traversal and control-character paths before
  filesystem resolution. Reject cross-site browser requests to the local server.
- Stop repeated/cyclic cursors, repeated empty pages and excessive collection
  requests before committing a bad pagination checkpoint.
- Preserve cached reaction history and followed creators when a completed
  response is unexpectedly empty or sharply truncated. A genuine bulk removal
  may require explicit local profile reset; a suspicious response cannot silently
  discard first-observed history. Normal small removals still reconcile.
- Serialize collection start/reservation for the same block. Ignore nonfinite
  Retry-After values and stop safely rather than sleeping on excessive delays.
- Remove the unused legacy artist-crawl GET endpoint and return a controlled
  error for unreadable static files.
- The owner exception uses a ninth additive migration with no quota reset or
  grant change. Community remains invitation-only. Other audit findings remain
  tracked in `3.0-audit-response-2026-10-24.md`.

## 3.0.0-beta.4 - Community authentication security patch

- Keep the write-capable Civitai credential on the local client. Community and
  registry use a separate UserRead + MediaRead OAuth grant (scope 33), protected
  in the existing OS-encrypted token store. The backend independently checks
  provider identity and the actual token scope before any Community data operation.
- Fresh Civitai sign-in is required for hosted features after updating. The login
  flow obtains the narrower grant through Civitai; no additional account or
  application consent checkbox is introduced. Old profiles never fall back to
  forwarding their write credential. Daily Gallery remains independent.
- Remove the attacker-chargeable project-wide 30/minute authentication bucket.
  Keep distributed credential/member limits and bounded request concurrency.
  Invalid credentials no longer consume another user's fixed request budget.
- No database migration, quota reset, invitation change or public activation.

Previous beta versions send their normal OAuth access token to the hosted service.
This is unnecessary privilege exposure, not evidence of a confirmed token theft.
Close older beta instances, update, then sign in again. Provider/gateway DDoS and
billing protection remain separate from application limits; arbitrary token floods
can still cause real load and require operator monitoring.

## Earlier beta work

- Beta-specific title, browser/tray identity, Windows executable/folder and purple
  B icon adapted from the repository's MIT-licensed generated mark.
- Authenticated Community remains visible independently of invitation. Invite-only,
  revoked/expired, blocked, read-only, maintenance and unavailable states are distinct.
- Application-wide registry is independent of Community membership. Fresh Civitai
  UserInfo supplies identity for automatic registration, with 12-hour activity
  throttling and owner-only aggregates/deletion. Hosted collection stays disabled
  until deployment and acceptance checks complete.
- Owner-operated local administration uses existing secure project access and a
  private invoker procedure. No separate Supabase Auth moderator identity is
  required. Audit uses an explicit owner label, not per-moderator attribution.
  Ordinary clients and runtime credentials have no administrative access.
- Shared PostgreSQL request admission limits upstream amplification across function
  instances. It does not limit billed invocations or replace provider monitoring.
- Beta updater rejects stable/wrong-channel packages, verifies tag-to-commit identity
  and checks archive digest plus embedded application identity. Source update tooling
  rejects dirty worktrees and avoids merges, resets and ignored-file overwrite.
- Candidate schema adds versioned registry and owner administrator migrations after the
  unchanged private-beta security migration. Hosted application backup restoration
  was tested in an independent PostgreSQL cluster before any migration.
- Fixed a browser-test race that aborted the valid resumed pagination request;
  production infinite-scroll logic is unchanged.
- Replaced recursive deletion of old update entries with atomic same-volume
  renames, report incomplete rollback explicitly, and make failed unattended
  helpers exit nonzero without a blocking startup dialog.

## Preservation and known limits

Daily Gallery and personal persistence remain separate. No personal database
migration or OAuth-session import is introduced. Stable 2.2.1 is not modified.
Owner-only hosted registry acceptance passed on 2026-10-23 with one legitimate
owner row retained. The earlier bounded registry test window has expired and collection remains off.
Community access is now restricted to explicitly invited identities; hosted policy
is controlled separately from the package. Old owner staging recommendations were
cleared only with explicit approval and a verified scoped backup. Eight migration
histories are unchanged. Fixture/native tests remain distinguished from real hosted
acceptance; this release publication performs no recommendation writes.

The Windows candidate is a portable folder ZIP, not a signed installer or a
standalone single-file executable. Real fresh packaged-client OAuth and owner-only
registry registration, idempotency, heartbeat throttling and post-expiry closure
have passed. Any rebuilt publication artifact needs its own exact-byte acceptance;
it cannot inherit another executable's OAuth result silently. Linux application
execution is unverified and explicitly waived by the owner.
GitHub Issues is the approved general contact; the owner is the initial operator,
and routine log/throttle retention has a 90-day target. That target is not a
claim of implemented 90-day history/purge. The private sensitive channel, remaining
retention periods, custody and operating commitments still need owner decisions
before distribution or collection/activation.
The operations and privacy guides contain the current decision register; no
separate moderator Auth account, consent banner or registry checkbox is required.
