## Before public release: production/development separation and secret custody

**OPEN — owner requested October 31, 2026.** Prepare and approve the environment
split and credential-custody plan before public launch. This records work to do;
it does not create an organization/project, buy a plan, move data, configure
GitHub secrets, or authorize an automated deployment.

Supabase projects provide separate databases and project configuration. Separate
organizations are useful for different billing plans and administrative access;
they are not required just to have development and production projects. Supabase
bills at organization level, and projects on different plans require separate
organizations. Proposed arrangement: retain the current staging organization and
project for beta/development, and evaluate a new production organization/project
with a separately approved plan and budget. Do not upgrade, rename, transfer or
repurpose the live beta project merely to establish this split. The owner's
screenshot shows the current organization labeled Free with one project; this
is not a detailed billing or usage verification.

Record and validate before cutover:

- Exact organization/project IDs for development/staging and production, owner
  access, costs, backup capability and incident responsibility. Use separate
  project credentials and least-privilege management tokens where supported;
  shared human ownership or broad account tokens can still span both projects.
- Reproduce reviewed migration history, RLS, restricted RPC grants, Edge source
  and intended policy in the new project. Fresh projects must start disabled
  until acceptance. Demonstrate dev credentials cannot administer production.
- Decide explicitly whether any beta recommendation/member/invitation records
  move to production; no automatic copy of private records, sessions, device
  credentials, or operator secrets. Preserve the existing beta evidence.
- Pin the intended endpoint in each release configuration and verify the actual
  executable connects to its intended project. Published beta clients currently
  depend on staging; preserve their operation during a staged, reversible cutover.
- Rehearse deployment, backup/restore, rollback and emergency disable in the
  intended environments before declaring production ready.

Credential storage responsibilities:

| Credential/configuration | Intended storage and boundary |
| --- | --- |
| Supabase project URL and client publishable key | Release configuration if required; these identify a project and do not replace RLS or server authorization. Never substitute a privileged key. |
| Server-only runtime secrets | Supabase Edge Function secrets in the matching project; never in the Windows package or browser. Existing Civitai OAuth isolation remains unchanged. |
| Local owner administration token | Existing Windows Credential Manager workflow, scoped where supported; plaintext Desktop files are temporary handoff copies, not long-term custody. |
| GitHub Actions deployment credentials, if automation is approved | Separate `development` and `production` GitHub Environment secrets, supplied only to reviewed deployment jobs; do not upload the current broad owner token by default. |
| Backup/recovery encryption material | Separately reviewed recovery custody; GitHub Actions secrets are not a general owner-readable password vault or a demonstrated disaster-recovery solution. |

GitHub supports encrypted Actions secrets at repository, organization and
environment levels. Environment secrets and deployment protections are available
for public repositories; confirm the actual repository plan/configuration before
depending on a specific protection. Secret storage does not make arbitrary
workflow code safe: a job allowed to use a secret can misuse it. Review workflow
changes, restrict production deployment refs, use minimum job permissions, and
select protections compatible with a sole-owner approval process. Do not run
untrusted contributor code with production secrets. Fork pull requests normally
do not receive Actions secrets; do not bypass that boundary through privileged
workflow triggers. Do not store confidential keys in git, release manifests,
installer assets, build caches, artifacts or logs. Review rotation, revocation,
expiry reminders and recovery ownership for every adopted secret.
