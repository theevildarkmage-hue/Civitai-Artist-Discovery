# Supabase readiness and future deployment

Current local execution status and the disposable native PostgreSQL procedure are in the
[parity/security report](3.0-parity-readiness.md). PostgreSQL is unavailable on this host;
expanded SQL/RLS tests are prepared but unexecuted. Node transport fixtures do not replace
them. Apply both prepared migrations, in order, when validating a fresh isolated cluster.

## Lightweight architecture review — October 21, 2026

The prepared design remains a recommendation ledger, not a gallery backend. Persisted
data is limited to member ID/current attribution name, image/creator/member references,
acceptance week/time/status, audit events, short-lived rate counters and member-scoped
idempotency keys. There are no image binaries, prompts, large artwork archives, personal
reaction/follow histories, OAuth tokens or browser-supplied identities in the schema.
The desktop's shared Discovery services own rendering and personal actions. Existing
local metadata/thumbnail caches remain the source for browse/detail enrichment.

| Requirement | Current prepared mechanism / tradeoff |
| --- | --- |
| Identity and ownership | Fresh Civitai UserInfo for every Edge operation; fixed-host REST and image.get checks establish a public, scanned, published still image and its creator before submission. Desktop simulator identity is never accepted by Edge. |
| Three member / three artist recommendations per UTC week | PostgreSQL member/artist/image advisory locks, server clock and counts of all accepted rows, including withdrawn/moderated entries. Browser quota labels are informational. |
| Duplicates, replay and atomicity | Global image-ID uniqueness; member-scoped idempotency; acceptance, audit and request-key insertion in the same transaction. Withdrawal does not refund quota or permit re-recommendation. |
| Authorization | RLS enabled, ordinary-role table access denied, PUBLIC function execution revoked, service-role RPCs used only from Edge. Moderation is server/operator-only. Actual deployed role tests remain pending. |
| Ratings and content controls | Submission verifies matching authoritative rating values. Viewer filtering revalidates locally cached ownership/rating/tags against that account's controls. Rating metadata is not duplicated into the cloud table; this keeps the ledger small but requires desktop metadata on a cold browse. |
| Efficient browsing | Partial active-sequence cursor index, bounded page size, member/week and artist/week indexes. Gallery returns references and attribution only. |
| Request volume / cost | Batched existing creator/reaction services and per-artwork local caches avoid new cloud gallery APIs. Opening uncached details adds one bounded local metadata read; it does not upload archives. Fresh cloud auth/ownership checks deliberately trade requests for revocation/ownership reliability. |
| Abuse and retention | Token/member throttles, bounded bodies/timeouts, redacted errors and short-lived rate buckets exist. Perimeter/IP limits before invalid-token work, operational ceilings and retention/backup policy remain required before public deployment. |

No backend redesign or migration was needed for UI unification. Keep the versioned
`verify` operation for current contract/tests, but avoid a separate preview request in
the normal one-submit modal. Consider removing unused preview operations in a future
API version, not by breaking v1. Do not add cloud profiles, reactions, image storage,
realtime subscriptions or a second artwork metadata archive. If cold-cache volume proves
costly, measure first; a minimal verified rating hint may help indexed selection later,
but must never substitute for account controls or become a large metadata copy. Existing
SQLite tests and mocked Edge transport do not prove PostgreSQL locking/RLS or platform
limits. The remaining isolated staging checklist below is still required.

**Nothing in this directory has been deployed.** Provisioning a project, supplying
production credentials, pushing code or publishing a release requires explicit approval.
The local milestone does not require Docker, Supabase CLI, PostgreSQL or a live project.

## Prepared artifacts

- `supabase/migrations/202610140001_community_v1.sql`: schema, indexes, RLS, denied
  ordinary-role access, private service-role RPCs, rate counters, moderation/audit and
  transactional quota enforcement.
- `supabase/functions/community-v1/index.ts`: bounded HTTP handling, strict artwork
  parsing, fresh UserInfo validation, public REST + tRPC artwork ownership verification,
  rejection of client identity fields, and privileged RPC calls kept on the server.
- `supabase/config.toml`: `verify_jwt=false` for opaque Civitai OAuth bearer tokens.
  This disables the Supabase JWT gate, **not** application authentication; the handler
  verifies every operation independently with Civitai before accessing community data.
- `supabase/.env.example`: placeholders only. No secret is in source or desktop config.

The SQL function locks member, artist and artwork in a consistent order, rechecks the
clock after waiting, checks existing accepted rows and both caps, and inserts the
recommendation/audit in the same transaction. Counts include withdrawn/removed rows.
Global unique image IDs additionally prevent duplicates. Lock hash collisions can
serialize unrelated traffic; they cannot permit extra slots. RLS alone is not the quota
mechanism. Functions explicitly revoke PostgreSQL's default PUBLIC execute privilege.

## Isolated project checklist (approval required before execution)

1. Choose a dedicated development project/region and confirm costs and retention.
2. Apply the migration as an administrator. Verify RLS enabled and `anon` /
   `authenticated` cannot read/write tables or execute community RPCs.
3. Put the project's service-role secret in Edge secret storage only. Do not copy
   `.env.example` values into source control or desktop settings.
4. Deploy the versioned Edge Function with the supplied JWT-gate configuration.
5. Configure platform request/body limits, concurrency ceilings and a perimeter/IP
   limiter before UserInfo. The application token/member limiter is supplementary;
   random bogus tokens must not be able to generate unbounded upstream checks or rows.
6. Configure log redaction: no Authorization header, request bodies, OAuth errors,
   complete UserInfo payloads or privileged keys. Keep aggregate outcome/latency only.
7. Use dedicated Civitai test accounts; verify OAuth UserInfo and authenticated fixed-host artwork API
   retrieval behavior, all five ratings, tag controls, revoked tokens and schema shapes.
8. Run actual PostgreSQL concurrency and Edge contract tests below. Confirm upstream
   regions or public browsing restrictions are rejected rather than misclassified.
9. Establish a server-only moderation procedure using `community_moderate`; audit
   operator access externally. Do not expose a caller-selected moderator flag.
10. Set a minimal audit retention policy, backup schedule, restore test and incident
    contact before public use. Retain accepted rows to preserve global uniqueness.

## Executable integration tests

These are **not run** during the local milestone. Use a disposable approved database
with the migration already applied and `psql` installed. Credentials are environment
values, never committed or placed in command-line arguments by the test harness.

```powershell
$env:CAD_ALLOW_ISOLATED_DB_TESTS = '1'
$env:CAD_TEST_DATABASE_URL = '<isolated database connection from your secret store>'
python tests/community_postgres.py
```

This runs concurrent separate PostgreSQL connections racing for member slots, artist
slots and a duplicate image, plus the executable SQL rules/permissions test. Random test
records are cleaned only within the test's namespace. The SQL rule test rolls back its
own fixed test records. **Never run against an existing production community.**

```powershell
$env:CAD_ALLOW_ISOLATED_EDGE_TESTS = '1'
$env:CAD_TEST_COMMUNITY_URL = 'https://PROJECT_REF.supabase.co/functions/v1/community-v1'
$env:CAD_TEST_CIVITAI_TOKEN = '<designated test-account OAuth access token>'
python tests/community_production.py
```

The Edge smoke test checks authoritative identity, invalid token/link errors, versioned
contracts and that verification failures spend no quota. It deliberately does not
recommend real artworks. Acceptance tests with real dedicated accounts must additionally
confirm all identity/creator/rating/tag fixtures, concurrent requests through the actual
Edge runtime, token refresh/revocation, sustained throttling, Monday rollover in staging,
deleted artwork, moderation, and local hidden-thumbnail privacy. Do not use a client's
clock override to simulate production rollover; use staging database fixtures/controlled
test time in a separate test-only function, never a time parameter in the deployed RPC.

The local Edge transport harness executes the actual TypeScript handler under Node
with mocked upstream/RPC transport; it is useful for boundary checks but does not
establish Deno runtime, PostgreSQL locking, gateway configuration or live Civitai behavior.
The TypeScript source was also checked with strict TypeScript using a minimal ambient
Deno declaration. Actual Deno checking and database execution remain isolated-environment
checks, not claims inferred from SQLite passing.

## Switching the desktop adapter

Only after staging validation and deployment approval:

```powershell
$env:CAD_COMMUNITY_MODE = 'supabase'
$env:CAD_COMMUNITY_URL = 'https://PROJECT_REF.supabase.co/functions/v1/community-v1'
$env:CIVITAI_HISTORY_DATA_DIR = Join-Path (Get-Location) 'data-dev-3.0'
python server.py --port 8907
```

Do not use the fixture launcher for this command: it intentionally selects fixture/local
mode. No UI rewrite or privileged desktop secret is required. Python refreshes/retrieves
the existing OAuth token and sends it server-to-server over HTTPS. The Edge Function
verifies it; it never accepts a local fixture identity.

## Release and rollback plan

Keep API v1 deployed while clients depend on it. Additive schema changes first, then a
compatible Edge release, then the desktop release. A future breaking API gets a separate
versioned endpoint. Snapshot the database before migrations and rehearse restoring into
an isolated project; do not destroy accepted/audit records to roll back a UI bug.

If shared service health fails, set `CAD_COMMUNITY_MODE=offline` or return a controlled
503 from the Edge Function. Personal Discovery continues to work. Roll back the Edge
version or desktop adapter configuration independently. Local fixture/community rows
are test data and are **not** automatically uploaded into the live community. The 2.x
installation and release history remain available throughout development.

The prepared October 15 migration adds member-scoped idempotency and a service-role-only RPC wrapper. Neither migration nor PostgreSQL transactional/RLS behavior was executed on this workstation: psql/postgres/pg_ctl and a running server are unavailable; Docker is installed but its daemon is stopped. No infrastructure was installed or started. See [submission validation](3.0-submission-validation.md).
