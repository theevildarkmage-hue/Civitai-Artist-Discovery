## Emergency disable and rollback

On a failed live gate or security/data-integrity concern, stop additional tests
and publication/distribution. Verify the actual Production target, set
`COMMUNITY_BETA_STATE=disabled` and `DISCOVERY_REGISTRY_STATE=disabled` using private
Production authority, then verify both secret digests and unavailable new identity
enrollment. Set readiness false; retain the recorded prior access mode and do not
erase audit/quota history. Disabled features do not guarantee zero session-renewal
traffic or revoke existing credentials. Use existing audited device-revocation or
blocking actions for a confirmed affected identity; broad credential rotation and
provider shutdown need a deliberate incident scope.

If the v2 function correction itself is defective, keep participation disabled and
prefer a reviewed forward fix. The previous function definition is preserved in
v1 source and the encrypted prechange capture. Do not fake migration history or
drop tables to regain an old seal. Restoring a backup over hosted data can lose
new legitimate writes and requires a separate approved recovery operation.

For a local updater failure, retain the update journal/staging/compatible backup
and use the matching helper recovery procedure. To roll back manually, close the
test application and restore the matching old package plus its matching protected
profile copy; never run 3.0 data under 2.2.1 without tested compatibility. Local
rollback does not undo Community writes. If release distribution must be stopped,
hide/remove the faulty release assets only under the incident owner's explicit
scope; publishing a lower version does not force installed clients to downgrade.
