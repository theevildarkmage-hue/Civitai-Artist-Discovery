# Native PostgreSQL security validation

This milestone supersedes the PostgreSQL-unavailable status in the earlier parity report.
It uses native Windows PostgreSQL 17.11, with no Docker, WSL, service installation,
administrator operation, global PATH change or production connection. It does not deploy
Supabase. The desktop's persistent SQLite data is outside this test environment.

## Verified distribution

[PostgreSQL's official Windows page](https://www.postgresql.org/download/windows/) links
to [EDB's portable binaries](https://www.enterprisedb.com/download-postgresql-binaries).
The 17.11 Windows x64 link resolved to:

`https://get.enterprisedb.com/postgresql/postgresql-17.11-5-windows-x64-binaries.zip`

The adjacent publisher `.sha256` matched the downloaded archive:
`80379b2c04d51c30225532e0ae04509899141e9957ed096fe749d7fd9df8f82f`.
The archive is 381,531,864 bytes. Only `pgsql/bin`, `pgsql/lib` and `pgsql/share` were
extracted under the current user's LocalAppData `CAD3Tools/postgresql-17.11-5` directory.
The executables report PostgreSQL 17.11. No pgAdmin/StackBuilder or Windows service was
installed. Distribution URLs, hashes and private paths are recorded in ignored evidence.
Recheck the official page and checksum before any future different download; do not
reuse an assumed latest-version URL or an unverified mirror.

## Reproduction and isolation

From the 3.0 checkout, with the verified binaries available:

```powershell
.\.venv-3.0\Scripts\python.exe -B scripts/validate-postgres.py `
  --bin "$env:LOCALAPPDATA\CAD3Tools\postgresql-17.11-5\pgsql\bin" `
  --repeats 5 --output reports/native-postgres-2026-10-21/validation
```

The runner always initializes a new OS-temporary `cad3-native-pg-*` cluster outside the
repository. It never accepts an existing database URL. It chooses a free loopback port,
binds only `127.0.0.1`, generates independent random administrator/application-role
passwords, and requires SCRAM-SHA-256. A wrong-password probe must fail. The bootstrap
password file is removed after initdb; passwords stay out of command arguments, reports
and committed files. SQL setup is sent through stdin, with statement/error statement
logging disabled. No production credentials are reused.

Only the dedicated administrator and `anon`, `authenticated`, `service_role` test logins
are allowed by the cluster's HBA rules; application logins are limited to the uniquely
named test database. Ordinary logins have no schema creation, table, sequence or RPC
access. `service_role` has BYPASSRLS and only the intentionally granted RPC execution
rights. The administrator creates/applies migrations and inspects test state; application
authorization tests use actual restricted-role sessions, not just administrator queries.

The SQL suite requires the runner-provided system identifier and data-directory match
before mutation. Non-loopback URLs, embedded password URLs and missing cluster proofs
fail closed. The harness parses connection coordinates into libpq environment variables:
putting a URI in the PGDATABASE environment default is not URI expansion.

The runner stops only its freshly created data directory with `pg_ctl` in `finally`.
It does not enumerate or terminate unrelated PostgreSQL processes. Windows background
startup writes to a file rather than inherited capture pipes, avoiding a wait for the
server's entire lifetime. The stopped cluster and logs are retained outside Git for
inspection; ephemeral plaintext bootstrap credentials are removed. Any future deletion
should resolve and inspect that exact owned directory first. No recursive cleanup of
existing installations or application profiles is performed.

## Migrations and defects fixed

The runner applies each migration transactionally, in filename order:

1. `202610140001_community_v1.sql` — ledger, constraints, indexes, RLS and RPCs.
2. `202610150001_submission_idempotency.sql` — member-scoped atomic replay keys.
3. `202610210001_community_rpc_guards.sql` — nullable-input guards and explicit privilege
   restrictions, with no table/column additions or stored-data rewrite.

The first two migrations intentionally create objects once; a second application is
rejected transactionally with the existing schema/ACL fingerprint unchanged. The new
CREATE OR REPLACE/revoke migration is safely reapplied. Fresh-cluster runs establish
repeatable installation; no SQLite or production migration is part of this procedure.
Only built-in `plpgsql` is required. PostgreSQL 17.11 is tested; do not infer deployed
Supabase-version/extension compatibility from that alone.

Real testing found two SQL three-valued-logic defects. `p_limit=NULL` made the old guard
evaluate to NULL and allowed an unbounded gallery LIMIT. `p_preview=NULL` skipped
insertion but returned success. Explicit null rejection fixes both; null member/image/
creator/name arguments now return the intended INVALID_REQUEST instead of incidental
constraint failures. Null/empty throttle keys and invalid moderation arguments are also
rejected explicitly. Quotas, lock ordering and stored data are unchanged.

Explicit table/sequence revocation also protects the RPC-only boundary when deployment
defaults grant more than a fresh native cluster. A permissive-grant fixture is installed
before hardening to test this. Schema CREATE is revoked from PUBLIC/application roles so
SECURITY DEFINER's public search path cannot be populated by untrusted callers. Apply
this only to the intended dedicated community project; shared-schema privileges need
review before deployment. Do not regrant direct write access to reduce test failures.

Edge validation now rejects JSON null/non-object/array bodies as INVALID_REQUEST and
requires the exact application/json media type (parameters allowed). Previously null
caused a generic 503 and prefix matching accepted application/jsonjunk. Responses remain
redacted. No cloud identity model or metadata catalog was added.

## Actual PostgreSQL coverage

`tests/community_postgres.py`, launched by the owner runner, uses independent psql
connections and real password-authenticated role sessions. Each invocation includes:

- Concurrent member/artist quota and cross-member duplicate submissions.
- Ten delegated member IDs accepting exactly three recommendations each and rejecting
  the fourth. These are trusted service-provided IDs, not ten verified OAuth accounts.
- Five barrier-synchronized rounds of two contenders for one member slot, six contenders
  for one artist slot, six duplicate contenders, and six identical replay requests.
  Each quota/duplicate race accepts one; identical replay accepts once and returns five
  replays, with one audit/request key. Conflicting keys/images also accept only once.
- Anonymous/authenticated SELECT/DELETE denial on all five tables, INSERT/UPDATE denial,
  denied RPC/role/schema escalation and cross-member reads, including absent/malformed/
  expired-looking/revoked-looking caller-controlled claims.
- RLS itself on all five tables under each ordinary role after temporary rolled-back
  SELECT/INSERT grants: forged role claims return zero rows and inserts are rejected.
- Self-recommendation, invalid/null IDs, global duplicates, UTC timezone independence,
  previous-week fixture isolation, and a Sunday/Monday offset constraint boundary.
  A real live Monday clock transition remains an isolated staging exercise.
- Injected audit failure and explicit rollback: no partial member/recommendation/replay
  persists, quota is preserved, and a later retry succeeds.
- A confirmed external lock holder, bounded lock-timeout rollback and retry after release.
  A deliberately reversed pair of external locks produces one deadlock victim and one
  successful transaction; retry then succeeds. This is server recovery testing, not a
  claim that the production fixed-order RPC produced a deadlock.
- Thirty-request throttle exhaustion/expiry plus six simultaneous requests competing
  for two remaining rate slots. Exactly two pass; four receive RATE_LIMITED.
- Final accepted-record/audit consistency, per-member limits, and removal of only the
  randomly namespaced test rows. The runner independently checks cleanup before Edge tests.

The five-repeat command executes 25 synchronized rounds per scenario on a fresh cluster.
No SQL session setting authenticates a JWT or proves revocation. RLS remains default deny;
Edge is the trusted identity/ownership authority. The privileged service key must never
reach clients: a holder can intentionally call identity-accepting RPCs.

## Edge boundary and outstanding staging work

`node --experimental-transform-types tests/community_edge.mjs` executes the actual handler
with synthetic transport and tests request limits, parsing, fixed hosts, spoofing,
ownership/metadata rejection, expiry/revocation responses, routing and redacted errors.

The native runner also executes `tests/community_edge_postgres.mjs`: actual TypeScript
handler, real service-role PostgreSQL RPC transactions, synthetic UserInfo/artwork
responses and a small test SQL adapter replacing PostgREST. It verifies ten propagated
member IDs, rejection without quota consumption, concurrent replay, a final-slot race and
actual persisted recommendation/audit/request-key counts. This is stronger than a mocked
database test; it is not Deno, PostgREST, the Supabase JWT gateway or live Civitai testing.
The subsequent [local Community service milestone](3.0-local-community-service.md)
installed portable Deno and PostgREST and added actual HTTP validation. The SQL
adapter remains a separate lower-level test; it is not counted as real HTTP evidence.

Before deploying, use a separately approved isolated Supabase project and dedicated Civitai
test accounts. Confirm exact PostgreSQL version/roles/default grants, apply all migrations,
store service credentials only at Edge, configure `verify_jwt=false` for opaque Civitai
OAuth tokens while retaining fresh UserInfo validation, and test real PostgREST RPC/errors,
token expiry/revocation, authoritative artwork shapes/ownership, request/retry limits and
concurrent commits. Configure ingress/IP throttling before random invalid-token work,
operational cost/concurrency limits, moderation, retention, backup/restore and redacted logs.
`community_production.py` remains opt-in and unexecuted without that environment.

Exact local outcomes, failures corrected, commits, integrity comparisons and logs belong
to the ignored `reports/native-postgres-2026-10-21/` evidence, not public runtime artifacts.
