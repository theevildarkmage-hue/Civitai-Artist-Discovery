# Linux stable-source correction: engineering verification

Date: November 6, 2026. Issue: [#32](https://github.com/theevildarkmage-hue/Civitai-Artist-Discovery/issues/32).
Base: `2de684ea55456afc118a22a968a9df8ee33ea89a`, the original stable v3.0.0 source.

## Change and root causes

A Linux user checked out the stable tag and ran `uv run server.py`. The immutable
tag's unfrozen build defaults still selected beta.14 and Development identity.
Separately, `build_community` defaulted source execution to a **local ledger**, not
the hosted public feed. Local status returns real Civitai identity and
`development:false` but no hosted `beta` policy object; that flag means the
verifier is not synthetic, not that the selected service is Production. These
two independent selections explain the reported beta version/local empty feed
and policy inconsistency. The exact original browser lifecycle was not reproduced.

`server.py --stable` now selects a fixed stable release configuration before
clients import. Community uses its reviewed Production endpoint and hosted
policy. Fixture mode is rejected; source test identities/controls and development
diagnostics are disabled at the release boundary. No arbitrary endpoint or
configuration-file override was introduced. The unflagged Development path and
packaged configuration loading remain available as before.

Default stable-source data lives in `data-production-3.0/` and ignores the
Development profile selector. Since Linux keyring identity is scoped by the
resolved data path, its protected account is also separate by default. Existing
advanced data-directory overrides are preserved; documentation explicitly warns
against using one to share a Development or running profile. Users sign in afresh
to enroll in Production. Nothing copies Development cloud identity to Production.

The configuration endpoint exposes non-sensitive version/channel/environment
fields, and source instructions distinguish the original tag from source
containing this fix. UI Community Beta wording is tracked separately in #27.

Stable-mode isolation run preloads `discovery.build_config` with `--stable`, then
resets the test runner's argument list before executing the unchanged suite with
runpy. It changes only release selection; no real OAuth credentials are used.

The new actual-server test verifies version `3.0.0`, environment `production`,
channel `stable`, server-controlled Community policy, signed-out identity,
unauthenticated gallery denial (401), and absence of a local Community ledger.
Chromium confirms the stable version/title and visible sign-in control with zero
page errors. It does not fake an authenticated public gallery.

Two initial harness attempts failed before correction: the Windows venv launcher
prevented PID-based HTTP ownership recognition, and direct invocation of the
existing Community beta test omitted the checkout from PYTHONPATH. Re-running
with the base interpreter and explicit test import paths passed. These were
harness failures, not evidence of working Linux sign-in.

## Integrity, security and limitations

No hosted writes, migrations, schema edits, feature activation, deployments,
release replacement or tag changes. No existing personal profiles were opened or
moved. Fresh isolated test stores use existing schemas. Existing Windows package
bytes and running installation remain unchanged. OAuth/access/refresh credential
handling and the signed-identity architecture were not changed.

No full release gate, Windows rebuild/updater/native packaged gate, full Node
suite or exhaustive browser suite was rerun. Those remain needed if producing a
new distributed release. This source correction is not a Linux binary package.

Real Linux desktop Secret Service, browser callback, OAuth enrollment and
Production artwork rendering are **not verified here**. The available Ubuntu WSL
distribution could not start because required host virtualization was unavailable;
no host configuration was changed. Linux remains experimental. Existing synthetic
Linux storage checks do not replace that real-user verification.
