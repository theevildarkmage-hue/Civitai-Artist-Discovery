Date: November 6, 2026. Issue: [#32](https://github.com/theevildarkmage-hue/Civitai-Artist-Discovery/issues/32).

## Change and root causes

A Linux user checked out the stable tag and ran `uv run server.py`. The immutable
tag's unfrozen build defaults still selected beta.14 and Development identity.
Separately, `build_community` defaulted source execution to a **local ledger**, not
the hosted public feed. Local status returns real Civitai identity and
`development:false` but no hosted `beta` policy object; that flag means the
verifier is not synthetic, not that the selected service is Production. These
two independent selections explain the reported beta version/local empty feed
and policy inconsistency. The exact original browser lifecycle was not reproduced.

`server.py --stable` now selects a fixed stable release configuration before
clients import. Community uses its reviewed Production endpoint and hosted
policy. Fixture mode is rejected; source test identities/controls and development
diagnostics are disabled at the release boundary. No arbitrary endpoint or
configuration-file override was introduced. The unflagged Development path and
packaged configuration loading remain available as before.

Default stable-source data lives in `data-production-3.0/` and ignores the
Development profile selector. Since Linux keyring identity is scoped by the
resolved data path, its protected account is also separate by default. Existing
advanced data-directory overrides are preserved; documentation explicitly warns
against using one to share a Development or running profile. Users sign in afresh
to enroll in Production. Nothing copies Development cloud identity to Production.

The configuration endpoint exposes non-sensitive version/channel/environment
fields, and source instructions distinguish the original tag from source
containing this fix. UI Community Beta wording is tracked separately in #27.

### Additional implementation: portable regression evidence

No application runtime code changed in this follow-up. Added
`tests/linux_secret_service_native.py`, which creates a private D-Bus session,
temporary HOME/XDG paths, separate profile and unlocked GNOME keyring with a
generated test-only password. It stores synthetic OAuth canaries through the
real app storage API, reads them in a separate process, confirms no DPAPI/token
file is written, checks encrypted keyring files for plaintext canaries, confirms
transient assertions are discarded, and deletes only its test credential. It can
run an existing test suite inside the same private keyring. It does not obtain or
use any real OAuth credentials and makes no external provider requests itself.

Linux execution exposed Windows-specific assumptions in the existing OAuth
transport and enrollment tests: they required a DPAPI file even though Linux
correctly uses Secret Service. They also did not consistently scope keyring
accounts to each temporary test profile. Updated those assertions to inspect the
actual platform store, retain the original encrypted-file checks on Windows,
isolate keyring accounts, and clean up synthetic entries. The enrollment restart
test now validates actual cross-process Linux persistence with matching account
scope. These were regression-harness defects, not demonstrated app credential
exposures.

The first-launch browser script reused a fixed port across rapid server restarts;
on Linux its own previous connection state caused the safety guard's occupied-port
check to fail. Each launch now reserves a fresh ephemeral port; live/occupied
endpoint protection remains intact.
