# Community Gallery alignment — October 21, 2026

Community extends the existing Discovery gallery. It does not own a parallel artwork
renderer or personal social-action implementation. No cloud infrastructure was created,
and neither the daily 2.2.1 installation nor its global Python packages were changed.

## Shared presentation and service boundary

`static/app.js` exposes `DiscoveryGallery.createCard`, creator/reaction hydration and
card disposal. Daily continues calling its existing `card(artist)` adapter. Community
calls that same adapter with an explicit image list, no Daily archive date/seen tracking,
its pagination callback and an artwork-change attribution callback. Account permissions,
avatars, follower counts, follows, reaction states/counts, collection/content menus,
tag checks, detail dialog, lazy observation, thumbnail fallback, video lifecycle,
keyboard navigation and responsive `.gallery` geometry come from the existing services.
Both sources use `feedback.js` skeletons and retry feedback. A failed Community card
check now keeps the shared retry control instead of silently deleting the card.

Combined validation exposed an existing Daily race: `loadDay` awaited its block summary
and then hid build controls before checking whether a newer build had superseded it.
The stale-request guard now runs immediately after that await. A deterministic browser
scenario reproduces the hidden Stop button against the old controller and passes with
the guard, including cancellation afterward. This preserves intended Daily behavior.

The previous Community no-op services, blank reaction renderer, always-disabled write
permissions, hidden follow control, separate lazy observer and thumbnail-error overlay
were removed. Unused preview/thumbnail overlay CSS was removed too.

Community groups loaded recommendations by creator across cursor pages. Distinct image
IDs appear in the existing artist carousel; repeated IDs are ignored. Attribution follows
the current image, not the artist card's first recommendation. Grouping does not remove
ledger records, consume different quotas or equate visually similar but distinct artworks.

Intentional source differences remain: Community has its compact title/Recommend Art/
Refresh/quota toolbar, recommendation credits, cursor pagination and single native modal.
It has no date-based collection, model ranking, or Daily seen history. API v1 still accepts
public still images only. Shared video rendering/recovery remains covered by the existing
video suites; this milestone does not claim end-to-end Community video submissions.
Unknown creation dates are not replaced by recommendation timestamps. Uncached generation
metadata is fetched on opening details, not while rendering every gallery card.

## Authentication, actions and local persistence

Personal endpoints previously admitted only Daily/Time Machine image IDs, so merely
unhiding Community controls would have produced rejected writes. The server now also
admits IDs returned in an authenticated, filtered Community page. This admission list is
process-local, viewer/member-scoped, locked and capped at 2,000 entries. Unknown IDs and
other viewers are rejected. Each subsequent use rechecks the current content profile
and artwork cache. Evicted IDs require refreshing the gallery; the list is not a new DB.
Actual reactions still read Civitai's current reaction state before deciding whether a
write is needed, and return live counts with the delta. Community-only reactions do not
insert artwork into Daily or alter recommendation/audit rows. Existing SocialWrite,
collection and content-control gates continue to apply. Simulator selection never
substitutes for real OAuth outside a nonce-challenged isolated test process.

Details first reuse the existing local collector metadata. Missing details use the
existing bounded public-image request/normalizer and local metadata cache, with a
creator-name check and field allowlist. They are never uploaded to Supabase. Community
reaction hydration now receives Civitai's counts through the existing batched endpoint,
rather than displaying permanent zero placeholders. Partial/empty live stats merge over
the saved image counts, so a missing live field cannot erase a known Daily count.
No SQL migrations or database
replacements were introduced. Source restarts retain `-B`, preventing bytecode output
from reappearing after the launcher deliberately disabled it.

integration restoration sandboxes contained only the single `RealMetadataTest` image;
four thumbnail sandboxes contained public sample metadata and empty/simulated accounts;

## Validation and integrity

Use the combined guarded runner and `dev-smoke.py --restart` from the development guide.
Exact results, artifact locations and hashes are recorded in the local completion report.
`community_shared_actions` tests unknown-ID/account/control/removal admission, bounded
state, real handler decisions against mocked Civitai transport and local-only metadata.
`community_shared_browser` exercises grouped carousel attribution, follows, reactions,
counts, detail/menu/modal/mobile behavior with mocked social transport and an unchanged
disposable ledger. `community_ten_members` still commits 30 synthetic recommendations;
its pagination assertion now counts carousel images rather than duplicate artist cards.
`day_selection_race` covers delayed block summaries during an active build. `history_audit`
proves that a clean tip cannot hide a secret blob or personal path in an earlier commit.

The original recovery's 30 recommendation/audit rows remain byte-for-byte present. Before
activation, the persistent ledger already contained one additional accepted record dated
October 21 at 15:24 UTC, plus its audit/idempotency record. All 31 are preserved; acceptance
compares the current before/after state rather than deleting the extra record to force
an obsolete count. Personal profile/reaction/archive hashes are compared to readiness
and recovery baselines. Live smoke performs no recommendation or social writes.

Production PostgreSQL/RLS concurrency, deployed Deno/Edge, real account mutation and OAuth
revocation acceptance still require an approved isolated environment. The development
ledger's members remain simulated even when its artwork and OAuth gate are real.
