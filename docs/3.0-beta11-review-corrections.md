## Review corrections

The independent review correctly identified a High-priority forced-refresh retry
regression: request-local attempted state was lost while the browser retained
force=true. The original reproduction was repeated before changes: two attempts
each returned UNAVAILABLE after 4.005/4.004 s and each consumed 63 provider calls,
including completed background work. The old test only retried ordinary loads.

Corrective commit: `d13f2a7bf601371a618aff0839d9c0f5383514a7`.
Changed: ArtworkCache.refresh_boundary/gallery, MetadataCache.refresh,
CommunityClient.request/_read, local Handler query/reconnect handling,
oauth.community_authorization/reconnect_community, and Community browser state.

One intentional Refresh has one UUID and a server-assigned verification boundary.
Retry preserves the UUID; a second Refresh creates a new one. An ordinary load
carries no refresh context. Account/content-control invalidation and observed
OAuth completion discard the old operation. The context is account/control-bound,
profile-local, capped at 64, and expires in 120 seconds without extension.
Unknown/expired/evicted IDs start fresh verification; malformed or incompatible
IDs fail closed. The identifier grants no access and is never forwarded to the
hosted handler. Workers recheck successful progress under admission to avoid a
completion/admission race. Existing pacing, global three-worker limit, ownership,
ratings and content checks remain. No schema or authorization change.

At 200 ms/provider call, 24-item forced operations now return an initial
UNAVAILABLE followed by success using exactly 72 total calls. Two consecutive
intentional refreshes each independently consumed 72 calls, with 24 items and
the correct cursor. Client-level operation durations were 5.20/5.24 s.
The Chromium test traversed the actual local HTTP handler, parameter parsing,
CommunityClient, SQLite and verifier parser; only authentication and upstream
responses were synthetic. It confirmed retry ID stability, different IDs for
new actions, no failed cursor advancement, account/settings invalidation and no
continuing replacement loop after leaving the page.

The original 60 ms scenario still passed: cold 24 items 2.768 s / 72 calls;
warm 0.009 s / zero extra calls. Four concurrent ordinary loads used 72 calls
total; simultaneous requests sharing a forced context did not duplicate all work.
Mixed expired/unavailable metadata returned 22 eligible items / 68 calls / 2.712 s.
Changed ratings, ownership and hidden content remain excluded.

The Medium custom-client defect arose because status depended on optional stored
enrollment metadata, while the direct reconnect's specific error was generalized.
Capability now derives from configured client. Unsupported state is stable across
protected-store reload and a child-process restart. Daily remains connected,
Reconnect is hidden, and desktop/mobile explain the built-in-client requirement
and need for fresh authorization if the owner manually switches clients.
The actual reconnect HTTP endpoint returns fixed UNSUPPORTED_CLIENT / 409 without
launching login, altering protected bytes, switching clients or revoking grants.
Built-in incomplete/outage/revoked/wrong-account tests continue passing.

H-01 storage, lock ordering, pending-rotation retention, replacement retry and
M-03 diagnostic implementations are unchanged. Their focused suites passed.

data changes. No existing real OAuth credentials were read. Existing application
databases, sessions and stable 2.2.1 remain untouched; all test data were disposable.
