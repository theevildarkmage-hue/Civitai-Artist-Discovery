# 3.0.2 archive startup disk I/O

The startup path reran `INSERT OR IGNORE INTO block_images SELECT local_date,id
FROM images` on every launch. Duplicate suppression still reads every image and probes
membership indexes. With millions of rows that causes substantial I/O even though no
new membership needs writing. Earlier release verification also combined a full
integrity read with same-drive database/thumbnail copying, amplifying contention.

A separate additive `archive_migrations(name,completed_at)` ledger now records the
membership backfill. Backfill and marker commit in one transaction. Existing populated
archives at Popular-index version 2 or later adopt the historical completion evidence:
repository history shows that version was committed after membership backfill in the
same transaction, and ordinary import/capture writers maintain memberships. Adoption
uses metadata and one membership lookup, with no image-table read. Missing or empty
legacy membership tables still backfill. A missing table is recovered even if a prior
marker exists. Index `user_version` remains independent and unchanged by this ledger.
Arbitrary externally edited or corrupt populated tables are not silently rebuilt.
Genuine legacy migrations can still require a one-time archive-sized operation; this
change removes repeated work, not the cost of necessary first-time migration.

Six new unit cases cover partial legacy tables, scan-free version-2 adoption, interrupted
empty tables, missing tables with a prior marker, rollback/retry on insertion failure,
and preservation of a future index version. Existing capture schema, capture recovery,
segment membership repair, history audit, archive calendar/window fallback, half-day
blocks/completion, Popular ranking and full-day progress suites passed (10 suites plus
the new suite). One invocation mistakenly named nonexistent `gallery_blocks`; that
harness error is retained, and the four correctly named gallery suites passed.

The isolated real acceptance archive completed adoption and a second check in 0.01s
with a SQLite authorizer refusing *every* image-table read. No image read was attempted,
index version remained 2, and the original installation was not opened for writing.
The Windows background-priority request returned false for this tiny check; its receipt
does not claim otherwise. The full-profile constructor preflight subsequently completed its twelve necessary
legacy half-day checks with 309.13 MiB of process I/O paced at 5 MiB/s and successful
Windows background I/O priority. A second complete HistoryArchive initialization took
0.006s with image-table reads forbidden. No full-day merge was pending, all 265 day
entries remained, and the established large-table counts were reused.

Operational safeguards for release preparation: reuse the completed verified backup
and already-verified database copies; keep partial regenerable thumbnail caches instead
of copying thousands more files; transfer necessary remaining files at at most 5 MiB/s;
run disk-heavy steps sequentially with background I/O priority where supported. Do not
repeat full integrity scans, whole-archive hashes or full database copies just to obtain
another receipt. Reuse established counts and integrity evidence, supplemented with
bounded indexed application checks. Snapshot/acceptance data remains isolated and never
synchronizes changes back to the original installation.

The legacy half-day boundary audit was another repeated membership/image join. Valid
results are now checkpointed in additive `legacy_block_coverage_audits`, keyed by block
and its saved bounds/update timestamp. Changed bounds or update timestamps require a
new audit; invalid blocks retain the existing reopen behavior and artwork is preserved.
Three additional regression cases prove unchanged blocks require no image reads,
changed timestamps re-audit (without replacing the old certificate on failure), and
changed invalid bounds reopen the block without deleting images. The existing
`collection_feed_boundaries` regression also passed. This relies on ordinary capture
writers updating the day checkpoint; arbitrary external SQL corruption remains outside
the automatic repair contract.

`--pause-auto-capture` pauses worker start/trigger for one process lifetime without
changing stored preferences. The API reports `sessionPaused`, and Settings shows
?Paused for this launch? with Run now disabled. Normal relaunch without the option
restores the saved schedule. Manual day builds remain available. This is used for the
acceptance launch so an existing enabled preference cannot immediately start heavy
background collection. Unit coverage exercises the repeated start/trigger paths and
normal relaunch; a separate browser suite validates the real CLI, API, settings save
and reload behavior. No original profile or authentication policy changes apply.

In-app restart now forwards an active session pause to the replacement process. The
real `source_restart` integration suite covers stable/development source, each with
and without a pause, checking actual replacement arguments and capture API status.
A normal independent launch without the option continues to restore the saved schedule.


Real-profile acceptance found a second automatic job: a saved analysis older than
24 hours schedules profile refresh ten seconds after opening the browser. The actual
snapshot's last analysis was November 14, so pausing capture alone would not prevent
unrequested startup work. `--pause-background-work` now pauses capture plus automatic
profile analysis for the session, without rewriting saved settings. Its summary policy
also cancels any pending automatic-analysis timer; explicit Analyse my reactions
remains available. The narrower --pause-auto-capture option keeps its original meaning.
In-app restart preserves either option. Default launches retain their previous refresh
policy and normal API response shape. No authentication or upstream write permission
changes are involved.

The actual CLI/API policy and browser scheduler are covered by
background_work_pause_browser, including cancelling a pending timer, a simulated minute
without automatic work, manual analysis through explicitly synthetic transport, saved
settings, and reload. profile_auto_refresh keeps its normal stale/recent assertions.
source_restart covers six real replacement combinations (stable/development, normal,
capture-only pause, all-background pause), including the replacement's summary policy.
The initial new test accidentally read its own mocked summary instead of the actual
CLI response; the fixture now reads the genuine server policy and uses it in the UI.
No existing security or progress assertions were weakened.
