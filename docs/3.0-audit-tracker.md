### Accepted architecture

**Community Gallery is Daily Gallery with a different source for the artwork list.**
Supabase supplies accepted recommendation IDs and governs identity/membership,
submission quotas, moderation and seven-day expiration. The local app uses shared
Daily metadata, filters, caching, image/video loading and rendering. Civitai access
and refresh tokens remain local. There is no browsing-triggered Supabase artwork
verification, separate Community tag/rating pipeline or three-record cold review.
See [the accepted design](3.0-beta11-accepted-gallery.md). These findings do not
authorize changing that architecture.

  they cannot simply be assumed retired.
- **Not demonstrated:** lost data, a failed actual incident recovery, an end-to-end
  current 14-migration data restore, or complete Supabase/Auth/Storage/secret recovery.
- **Existing protection/evidence:** fail-closed inventory checks; legitimate scoped
  encrypted recovery receipt; pinned migration/source history; current schema and
  permission recreation in native tests. The original DPAPI/custody limitations remain.
- **Owner decision:** no running-app change and no competing backup frameworks.
  This is the only concrete pending engineering-maintenance item established by

### Cached artwork ratings

**Classification:** ACCEPTED LIMITATION — NO CURRENT CHANGE. **Assessed:** 2026-10-27.

- **Affected:** [HistoryArchive/shared cache](../discovery/history.py),
  [shared Gallery admission and preview routes](../server.py), local Content Controls.
- **Demonstrated:** synthetic cached PG metadata remained PG when the configured
  synthetic provider would return XXX; that provider was not called. Existing rows
  have no rating-freshness TTL and may persist until normal ingestion updates them.
  They are persistent opportunistic metadata, not immutable historical truth.
- **Not demonstrated:** an actual upstream reclassification or a user seeing
  prohibited content. Selected levels are enforced against available metadata;
  the limitation is detecting later upstream changes. Seven-day recommendation
  visibility is not a seven-day metadata-cache TTL.
- **Existing protections:** shared known-rating checks, required hidden-tag preview
  gating, hidden images/creators, blocking and server moderation. None proves a
  cached rating is current; do not conflate tag checks with rating freshness.
- **Owner decision:** accept shared caching. No mandatory per-open Civitai checks,
  Supabase revalidation, Community-specific refresh pipeline or arbitrary TTL.
  This is not an unresolved critical vulnerability or an implementation ticket.
- **Reassess only if:** a credible real misclassification incident is reported;
  Civitai changes relevant API behavior; product requirements change; new evidence
  establishes meaningful content-safety harm; or a planned shared-cache change
  naturally requires reviewing freshness.
- **Minimum acceptance if reopened:** first establish the actual requirement and
  impact; examine shared Daily behavior, API cost, latency and offline/failure
  handling; justify the smallest viable policy. Any eventual correction must use
  the shared Gallery system and demonstrate selected-level/tag controls remain
  intact. Synthetic staleness alone does not justify choosing a policy.
- **References:** local Python reproduction and independent assessment above;
  [shared gallery browser coverage](../tests/community_shared_gallery_browser.py),
  [hidden-tag checks](../tests/hidden_tags_before_preview.py),
  [filter coverage](../tests/community_filters_browser.py).

### Invalid session-token lookups

**Classification:** MONITOR — REASSESS IF EVIDENCE CHANGES. **Assessed:** 2026-10-27.
Overlaps historical L-07; no additional implementation ticket.

- **Affected:** [identity entry point](../supabase/functions/community-v1/identity-handler.ts),
  [handler admission/denial cache](../supabase/functions/community-v1/handler.ts),
  [session resolver](../supabase/beta-migrations/202610240003_identity_sessions.sql).
- **Demonstrated:** 40 distinct syntactically valid invalid tokens caused 40 mocked
  resolver lookups and 40 HTTP 401 responses. Repeated invalid tokens benefit from
  the denial cache. No hosted attack traffic was generated.
- **Not demonstrated:** authentication bypass, sustained abuse, a service outage,
  material unexpected expense, or verified project-wide protection against attack.
- **Existing protections:** syntax/body validation, indexed opaque-session lookup,
  expiry/revocation, bounded per-runtime concurrency, bounded denial/admission
  caches and authenticated token/member limits. Per-runtime limits are not a
  project-wide ceiling. Invitation-only does not hide an internet-facing endpoint.
- **Dated operating evidence:** 24-hour interval ending 2026-10-27 13:41 UTC had
  49 recorded function requests: 43 HTTP 200 and six HTTP 401, peak three/minute.
  Database snapshot: 14/60 connections, one active. These showed no current service
  pressure, not sustained-attack resilience. The six 401s cannot be labeled attacks.
  Project-specific ingress controls, remaining quota and billing protections were
  not fully verified. These are historical aggregates, not continuous monitoring.
- **Owner decision:** no new limiter, attacker-exhaustible project-wide budget or
  resolver redesign to eliminate synthetic lookups. Authentication stays unchanged.
- **Reassess if:** sustained unusual authentication failures, abnormal DB/Edge load,
  material unexpected cost, legitimate-member authentication availability problems,
  a credible uncovered exploitation path, or hosting changes affecting protection.
- **Minimum acceptance if reopened:** inspect real traffic, verified platform
  controls, applicable quotas and failure patterns first; demonstrate any mitigation
  addresses actual impact, preserves legitimate access and cannot become an
  attacker-controlled lockout. Another token-keyed limiter is not a solution to
  token rotation, and client-supplied IP headers are not trusted identity.
- **References:** local Edge reproduction, aggregate receipt and independent review
  above; [handler/security tests](../tests/community_auth_security.py),
  [native HTTP authorization tests](../tests/accepted_feed_http_native.py).

### Renewal during feature disable

**Classification:** DECISION RECORDED — NO ACTION. **Assessed:** 2026-10-27.

- **Affected:** [identity request ordering](../supabase/functions/community-v1/identity-handler.ts),
  [device renewal](../supabase/functions/community-v1/renewal.ts),
  [client renewal](../discovery/oauth.py), [operations](3.0-beta-operations.md).
- **Demonstrated:** valid synthetic authenticated device renewal succeeded with
  COMMUNITY_BETA_STATE and DISCOVERY_REGISTRY_STATE both disabled, including a
  lookup, public username request and rotation. Disabled Community participation
  did not thereby become available.
- **Not demonstrated:** violation of an established complete-authentication-stop
  requirement, a real harmful incident or material renewal expense. Feature flags
  are not verified global infrastructure or billing shutdown mechanisms.
- **Existing protections:** device proof-of-possession, bounded lifetime, revocation,
  replay protection and rotation; client serialization/backoff and separate Daily
  credentials. Ordinary disabled requests also perform authentication work, so a
  renewal-only gate would not be a complete execution/spend cutoff.
- **Owner decision:** preserve renewal and authentication ordering; do not strand
  legitimate sessions to reinterpret feature flags. Operational wording now makes
  the distinction explicit. No outstanding Beta 12 bug is created.
- **Reassess only if:** owner explicitly requires complete identity-service emergency
  shutdown; a real incident shows harmful renewal; hosting/identity architecture
  changes; or a documented operational policy is found that the behavior violates.
- **Minimum acceptance if reopened:** establish the exact new requirement/policy
  and scope first; distinguish feature denial from platform shutdown; demonstrate
  containment and recovery without unnecessary session invalidation, Daily loss
  or a false zero-cost guarantee. No design is selected by this record.
- **References:** local Edge reproduction and independent assessment above;
  [session-renewal tests](../tests/community_session_renewal.py),
  [enrollment recovery tests](../tests/community_enrollment_recovery.py).
