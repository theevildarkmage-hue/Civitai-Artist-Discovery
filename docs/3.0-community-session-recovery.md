# Community card entry and session recovery

## Reproduced failures

A Daily card called the shared recommendation modal while its `submissions` flag
was still false. Only Community status loading initialized that flag, so the
first card action could return without a dialog or message. Previous Community
access errors also disabled that flag. Both entry points now obtain fresh
server admission/policy before opening the same modal. Denials are visible and
no recommendation is submitted just by opening it.

An authentication error paused the Community feed, but a later successful auth
state update did not reset that failed pager. The view now invalidates and reloads
after that event. Ordinary auth polling does not reset a healthy feed or scroll.

Read-only OAuth refresh redeemed a rotating refresh token and then performed
independent scope/account checks before saving it. A temporary verification
outage therefore lost the rotated replacement, leaving the consumed old refresh
token for the next attempt. Replacement credentials are now encrypted immediately
as a separate pending-refresh candidate. No pending access token is returned until
independent provider verification succeeds. A retry resumes verification instead
of redeeming the old refresh token again. A definitive rejection affects only the
Community grant, preserving the local Daily authorization.

An unchanged refresh response may omit scope under
[RFC 6749 sections 5.1 and 6](https://www.rfc-editor.org/rfc/rfc6749.html#section-6).
The client retains the previously verified exact read scope in that case, and
still checks actual token scope, OAuth subject type and matching account at the
provider. Explicit wider/malformed scopes remain rejected. Primary write-capable
tokens never substitute for the Community grant.

## Boundaries and verification limits

No database migration, hosted deployment, invitation, quota adjustment or policy
change is needed. Only the existing protected local credential envelope gains
an internal pending-refresh candidate during rotation. No tokens are logged.
Authentication recovery and provider outages are reproduced with synthetic tokens
and browser HTTP fixtures. This does not establish the exact provider response
seen by app1ecore, nor prove a five-hour real-world session. Retest the packaged
patch with that tester after publication; ask only for redacted error codes and
app version, never OAuth credentials.

Older clients cannot treat the separate pending candidate as an admitted token;
rolling back during a pending rotation can require a fresh interactive login.
There is no automatic replay of recommendation writes.
