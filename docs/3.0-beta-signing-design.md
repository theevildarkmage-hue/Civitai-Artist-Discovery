# Deferred beta update signing

The owner chose documentation rather than key creation on 2026-10-24. No signing
key, credential-store entry, recovery export or updater trust-root change is made
by this design. GitHub release authority and API asset digests remain the current
trust root. The Windows executable is still unsigned.

Proposed later milestone:

1. Review an Ed25519 implementation/dependency and define a beta-only public key
   embedded in the updater. Stable 2.2.1 must not share its update channel or key.
2. Define a canonical signed manifest containing application ID, beta channel,
   monotonic version, exact tag/source commit, asset name/size/SHA-256 and schema
   version. Verify before extraction/replacement, then retain existing path,
   package-identity, receipt, rollback and file-lock checks.
3. Create the private key only after approval, inside the owner-controlled release
   process. Keep it in Windows Credential Manager; never distribute it, put it in
   repository history/GitHub Actions secrets by default, or expose it to audit tools.
4. Choose separate encrypted recovery custody, passphrase handling, authorized
   recovery operator and an independent-account recovery exercise before claiming
   recovery. DPAPI-only export is not independent-account custody.
5. Test unknown/wrong keys, altered manifests/assets, channel substitution,
   downgrade/replay, interrupted updates and rotation/revocation. Distinguish
   detached update signatures from Windows Authenticode/SmartScreen reputation.
6. Plan a reviewed bootstrap release: existing unsigned-updater betas cannot gain
   independent authenticity for their first signed-updater download merely because
   a manifest is added. Document that transition and emergency replacement path.

Do not invent an automatic expiry/downgrade policy, recovery contact or rotation
authority on the owner's behalf. Pinning another GitHub-hosted digest alone does
not provide independent signing.
