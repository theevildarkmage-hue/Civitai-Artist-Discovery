# 3.0.2 session recovery candidate — issue #61

This is the first sequential 3.0.2 item. Source regressions and real-account
controlled-expiry renewal passed in the packaged preview. Full-release acceptance
remains required; this does not mark the complete 3.0.2 release ready. Items #60, #59, PR #57, PR #12, #27,
#36 and #29 have not been integrated in this candidate.

## Failure and implementation

An expired-token status snapshot disables reactions and follows while the backend
renews asynchronously. Previously, the browser applied that snapshot once and waited
for its five-minute interval; failed interval reads were ignored. Existing controls
could therefore keep a temporary disabled state after renewal succeeded. Their
tooltips incorrectly attributed every failure to missing OAuth scopes.

`static/ui/auth-session.js` now reconciles status reads for startup, Daily loading,
routine checks, explicit login and Community reconnect. Concurrent readers share
one request. Refreshing and offline responses schedule at most seven follow-ups,
after 1, 2, 4, 8, 15, 30 and 60 seconds. Each request times out after ten seconds.
The five-minute routine interval and returning to a visible tab start a new bounded
cycle. Ready, revoked and missing-scope responses end the recovery cycle.

Network failures retain cached identity but clear write capabilities until a new
server response confirms them. Sign-in/out invalidates old requests and timers;
even a transport that ignores cancellation cannot apply its old generation.
The browser never infers grants from remembered scopes or replays mutations.

The existing DOM is reconciled without rebuilding the gallery, so image selection,
reaction selections/counts and scroll position survive temporary renewal. Controls
explain refreshing, offline, revoked and missing-scope states separately.

Related lock defects discovered during implementation: blanket permission updates
could unlock pending follow/reaction actions, and a failed reaction could re-enable
its button after permissions became unusable. Reconciliation now preserves pending
locks; failed reactions recheck current permission. Late follow replies also check
the account epoch before applying state, matching the reaction isolation policy.

## Persistence, security and rollback

No schema changes, migrations, OAuth storage changes or backend endpoint/policy
changes are included. Existing protected credentials must not be cloned into a
second refreshing instance: shared rotating refresh credentials can interfere with
the original installation. An isolated interactive candidate needs its own sign-in.
Keep backups private and preserve the original installation and Git identity guard.

Rollback consists of closing the isolated candidate and returning to the original
installation. Its original data is never a migration destination. Candidate code
can be discarded or reverted locally without changing an archive schema. No remote
publication, release tag, hosted deployment or original-installation update is part
of this change.

## Local verification gate and disk I/O

The isolated Windows Development preview has been built from the recovery commit
using Python 3.14.8 / OpenSSL 3.5.9. Signed-out startup and the actual packaged
welcome screen show 3.0.2 and Development Preview. The frozen-module credential
isolation suite passed eighteen synthetic-boundary tests; it executes extracted
package modules under the test interpreter, so it does not certify real provider
authorization or replace interactive packaged testing.

The active authentication sandbox is deliberately empty. Automatic capture and
update checks are off in that sandbox only. Verified copies of personal databases
are reserved separately; no protected OAuth credentials were imported. Real-account
session renewal was the gate before proceeding to the next requested item.

Large local data operations must remain sequential and use background I/O priority
and bounded transfer rates. Reuse the completed SQLite online backups and existing
byte-for-byte database verification instead of recopying or rescanning unchanged
archives. Thumbnail caches are disposable and need not be migrated. Small preserved
settings, follows and creator-profile metadata were transferred separately at a
maximum of 5 MiB/s, with the original installation excluded as a write destination.

A separate startup issue was discovered while preparing the full-history launch:
`HistoryArchive._initialize()` unconditionally executes
`INSERT OR IGNORE INTO block_images(block_key,image_id) SELECT local_date,id FROM images`.
Idempotency avoids duplicate rows but still scans existing images and checks their
memberships on every launch. A large archive can therefore incur heavy I/O even
without a migration or copy. This is a source-confirmed mechanism, not a measured
large-profile startup in this candidate. Do not open the reserved large profile
until the migration is made safe and bounded with compatibility coverage. Do not
skip the backfill blindly for legacy archives or mark this issue repaired.

## Real-provider validation

After interactive sign-in, the connected identity matched the reserved profile. The
isolated packaged writer was stopped before changing only its DPAPI-protected local
expiry timestamp. The same open browser page then observed real backend
`refreshing` / writes-disabled and `ready` / writes-enabled responses, approximately
one second apart, without a reload. The provider returned fresh authorization; the
card and selected reaction/count remained intact. No authentication response was
mocked and no social action was sent. The displayed probe artwork was synthetic.
The original installation's encrypted credential file remained byte-identical.

This was a controlled local-expiry cycle with genuine Civitai renewal, rather than
a multi-hour natural-expiry soak. Two harness attempts did not pass: inherited
background-process pipes stalled the first; an unprepared probe card correctly
retained its artwork-loading reaction lock in the second. File-backed process logs
and a fully prepared local SVG probe corrected the harness without changing app
security behavior. Failed receipts remain private beside the final passing trace.
