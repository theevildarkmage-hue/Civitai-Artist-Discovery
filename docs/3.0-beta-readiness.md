**B: isolated private staging for validation**, after explicit approval, with
submissions disabled initially. Public distribution with submissions (C or D) is
blocked by hosted authentication, moderation and operational gaps below.

## Feature controls

`discovery/community_beta.py` contains a reviewed endpoint constant, currently None.
Production availability therefore remains off. A separately approved rollout change
must set that exact HTTPS Supabase function endpoint; frozen builds do not trust
an environment-supplied endpoint or fixture mode. A public endpoint is not a secret.
The per-profile `community-beta.json` stores only an explicit boolean preference.
Keeping it separate avoids changes to older settings parsing and preserves rollback.

| Install/user state | Behavior |
|---|---|
| New or upgraded install, no preference | Community disabled; no opt-in inferred |
| Rollout unavailable | Compact unavailable checkbox in My Profile; no announcements |
| Approved rollout, opted out | Tab hidden; personal features unaffected |
| Approved rollout, opted in | Community Beta tab; normal OAuth still required |
| Remote status absent/malformed/stale | New submissions disabled; cached browse may remain |
| Remote read-only | Browse remains; new submissions/verification/withdrawal denied |
| Remote disabled | Shared operations disabled; personal galleries remain |

The authenticated status response from the fixed HTTPS service is the integrity-
protected remote policy channel, not a client-editable configuration document.
No executable configuration or complex flag service is added. UI policy is only
guidance: the Edge handler checks server-owned `COMMUNITY_BETA_STATE` on every
authenticated operation. Missing/unknown values fail closed. `read_only` permits
gallery reads but rejects writes; `enabled` permits otherwise-valid operations.
`COMMUNITY_ALLOWED_RATINGS` defaults to `1,2`; invalid values fail closed and other
ratings reject before SQL persistence. Local stress launchers explicitly allow all
ratings and enable their disposable services; this is not production configuration.

Secrets can be changed by an authorized operator without shipping an application
update. Verify warm/cold-isolate propagation and measure the incident-disable delay
in staging. For immediate database enforcement while that propagates, revoke both
submission entry RPCs from service_role (see runbook). In-flight requests already
committed cannot be undone by a switch. There is no silent offline submission queue;
the existing persisted idempotency key supports an explicit retry after a lost reply.

## Authentication and ownership review

Civitai access tokens are external OAuth credentials, not Supabase JWTs. The function
uses `verify_jwt=false` solely to reach its own validation: fixed TLS UserInfo on
auth.civitai.com, fresh on each operation, bounded timeouts, no redirects. It validates
positive stable sub, checks id consistency when supplied, and accepts a bounded public
username. Member/uploader assertions from callers are not trusted. No refresh token,
email, IP address, prompt or full profile is stored in Community tables.

Opaque access tokens are not decoded to invent issuer/audience/expiry claims.
The trusted hub enforces token validity; no locally accepted JWT substitutes for it.
PKCE and state protect the desktop authorization-code flow; refresh is serialized
and rotating credentials are protected by the existing local OAuth storage. UserInfo
revocation behavior, tokens from different OAuth clients, account recovery, deletion,
rename consistency and actual token renewal failure require dedicated real-account
tests. Stable IDs preserve ownership across names, but account-merge semantics cannot
be assumed. A failed UserInfo call never falls back to a cached identity for writes.
The Edge function itself does not refresh credentials or cache successful UserInfo.

The [official Civitai OAuth guide](https://github.com/civitai/civitai/blob/main/docs/auth/oauth-developer-docs.md)
describes PKCE, the hub, UserInfo and rotating tokens. Local tests cover synthetic
expiry/revocation and stable-ID renaming; those tests do not establish live lifecycle
semantics. See [Supabase external-auth guidance](https://supabase.com/docs/guides/functions/auth)
before testing the configured gateway: removing the platform JWT check is safe only
when independent authentication remains mandatory on every operation.

Artwork uploader is resolved independently via exact Civitai listing and image.get.
Unknown/inconsistent/deleted owners and ineligible metadata fail closed. Numeric
uploader and authenticated member IDs are compared before persistence. SQL repeats
the inequality constraint. The service-role key can delegate IDs and must remain
strictly server-side; possession is administrative authority, not an ordinary user
capability. It is never compiled into the desktop or returned in policy responses.

## Minimum moderation before public submissions

Existing service-only community_moderate can hide/remove with an audit event; it is
not exposed as a user HTTP operation. Do not distribute its privileged key. Current
audit events do not identify moderator/reason, there is no report queue or persistent
submitter blocklist, and automatic rechecking of already-featured artwork is not an
operational moderation service. These are public-write release blockers.

Minimum next implementation: a bounded authenticated report endpoint with fixed
reason codes, one active report per member/image, rate limits and minimal retention;
an admin-only server handler with an explicit stable-ID allowlist or separate operator
identity; additive report/blocklist records; atomic hide/remove/block plus append-only
actor/reason/time audit. No browser service credentials or destructive deletes. Validate
authorization and fake moderator claims through HTTP before exposing administration.
Keep reports private; public feed exposes only artwork/uploader/recommender public
attribution. Emergency SQL actions require operator identity and an external incident
record until richer moderation audit exists.

Handle deleted/unavailable images by failing fresh submission verification and hiding
them from normal cached projection when revalidation finds removal. Changed ratings
must be revalidated with bounded freshness and moderation review; a 24-hour browse
cache cannot guarantee immediate removal. The new server rating policy restricts new
submissions, not historical rating drift. Define response ownership and removal SLAs,
report retention (proposed 90 days), accepted-record/audit retention (proposed one year,
subject to privacy review), and an appeal process before public writes.

## Privacy and retention

Community stores stable member ID/public username, image and uploader IDs, UTC time,
week, status, accepted/audit events and idempotency request keys. Short-lived rate
buckets contain SHA-256 token digests/member keys, not bearer values; cleanup removes
old buckets on subsequent traffic, not by a guaranteed wall-clock expiry job. Idle
clusters retain them until traffic or an operator job runs. Recommendations/audits
currently have no retention scheduler. Member IDs/names remain personal data despite
being public. Explain purpose, attribution visibility, retention, reporting/contact
and deletion constraints to participants; obtain a privacy review before public beta.
Image bytes remain on Civitai; no second metadata archive or image-hosting service is
introduced. Logs must omit request headers, tokens, UserInfo bodies, email and DSNs.

## Update channels and ordinary-user distribution

The 2.2.1 updater requests GitHub /releases?per_page=20 for the existing repository,
ignores drafts, compares semantic versions, requires the exact
`CivitaiArtistDiscovery-{version}.zip` asset and GitHub SHA-256 digest, validates the
download/extraction and preserves portable data. Stable versions ignore prerelease
flags AND prerelease version suffixes. Prerelease installs can receive later beta or
stable versions. Checks occur about every 24 hours or manually; a branch push never
becomes an update notification. No stable updater behavior changed here.

Recommended distribution: first private staging, then a separately approved ordinary
stable application update with Community default off and explicit opt-in, once public
blockers are closed. This reaches existing users without forcing beta behavior or
compilation. A standalone `3.0.0-beta.1` GitHub prerelease is useful for early testers,
but stable 2.2.1 users must download it manually: their existing updater intentionally
ignores it. Do not relabel prerelease code as stable merely to bypass that protection.
Development remains source branch development/3.0. Current build stays 3.0.0-dev;
no release version/tag is claimed until approved release criteria are met.

Frozen data now defaults to portable data/, matching the stable updater's preservation
boundary; source development remains isolated. Upgrade copies are tested without
OAuth tokens to avoid competing refresh-token rotation. Existing settings/databases
must be backed up before release; rollback must restore binaries, not overwrite data
with an old backup. The current schema adds no migration. Existing updater tests
cover interrupted copying/rollback and archive attacks; actual signed releases and
dedicated-account packaged OAuth consent remain external acceptance steps.

## Capacity model (assumptions, not performance measurements)

Assume four weeks/month, full use of three recommendations/member/week, 60 gallery
pages/member/month, four status reads/day (120/month), two Edge attempts per accepted
submission including preview/retry, and no realtime subscriptions. This yields 12
accepted records, 24 submission-related calls and 204 total invocations/member/month.
Assume 2 KiB per recommendation including indexes/audit/replay, 2 KiB per profile,
20 KiB/gallery response and 2 KiB/other response. Civitai media goes directly to its
CDN, not through Supabase. Actual Civitai calls vary with metadata/cache warmup and
retry rate; each commit verifies UserInfo plus two ownership lookups, and each
gallery/status request verifies UserInfo. Measure vendor throttling in staging.

| Users | Accepted/month | Edge invocations/month | Ledger growth/month | Estimated response egress/month |
|---:|---:|---:|---:|---:|
| 100 | 1,200 | 20,400 | 2.3 MiB + profiles | 145 MiB |
| 1,000 | 12,000 | 204,000 | 23.4 MiB + profiles | 1.42 GiB |
| 10,000 | 120,000 | 2,040,000 | 234 MiB + profiles | 14.2 GiB |

These exclude base PostgreSQL size, bloat/WAL, burst retries, abuse, logs and backups.
Repeated 60-second active-tab status polling increases the model; instrument real
session duration and cap rollout rather than treating 204 calls as an upper bound.
Audits and historical records accumulate even when recommendations are withdrawn.

Verified 2026-10-22 on [Supabase pricing](https://supabase.com/pricing): Free includes
500 MB database, 5 GB egress and 500,000 function invocations/month; Pro starts at
$25/month with 8 GB disk, 250 GB egress and two million invocations, with listed
overages. These are allowances, not assurances of workload fit or a spending cap.
Free projects can pause after inactivity; production backups/retention differ by
plan. No subscription was created. Recheck pricing before approval.

Start at 20-50 invited dedicated testers; cap at 100 until a week of measurements.
Review at 50% and alert at 70% of invocation, database, egress and log allowances;
disable writes at an agreed emergency threshold before 90%, accounting for delays.
Budget invocation abuse separately; a handler-level 429 still incurs an invocation.
Alert on auth failures, 429/5xx, SQL lock/pool waits, missing audit pairs, ownership
failures and queue depth. Do not log sensitive payloads to diagnose them.

## Reproduction and publication

Use scripts/build_exe.ps1 with -PythonExecutable pointing to the verified portable
Python 3.14.8/OpenSSL 3.5.9 runtime and an external -OutputRoot. The original private
Python 3.14.3 is below the existing release gate and was not used to bypass it.
`scripts/inspect-production-package.py` inspects PYZ/module lists and runs actual EXE
profiles; screenshots distinguish real unauthenticated welcome from UI-only fake
identity simulation. That simulation cannot authenticate backend requests.
Run the complete application suite, native runner, Deno checks and restart smoke
from the [local service runbook](3.0-local-community-service.md). Rebuild if source
or static assets change. Keep generated packages/reports and profile copies out of Git.

Prepare publication as a new snapshot commit parented ONLY to the existing clean
development/3.0 publication history, with the established public noreply authorship
and [skip ci]. Do not merge private 3.0 history: its reachable historical documents
contain personal paths. Preserve both histories. Scan every reachable candidate blob
with scripts/audit-history.py, not just tip files. Existing public release covers and
v2 screenshot/metrics artifacts are historical exceptions; no new reports/keys/data
belong in the snapshot. No workflows are added here, so there is no new automatic
stable-release trigger. Inspect any upstream workflow changes before pushing.

After explicit source-publication approval, review and run (never run automatically):

```powershell
git log --oneline development/3.0 -3
python -B scripts/audit-history.py --ref development/3.0 --output <private-audit-file>
git diff --stat development/3.0~1 development/3.0
git push origin development/3.0:development/3.0
```

Do not push tags or invoke a release workflow. Binary publication additionally needs
version/changelog approval, reproducible package inspection, archive digest, malware/
signature/reputation review, upgrade/rollback testing with dedicated accounts and a
draft release review. The command above publishes source only and cannot notify
stable updater installations.
