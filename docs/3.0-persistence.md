# Persistent profiles, metadata and Community Gallery

Implemented locally on branch `3.0`, 2026-10-14. No push, release, cloud deployment,
or changes to the daily-use 2.x application or port 8906.

## Root causes

Two different 3.0 directories were in use. The default launcher selected
`data-dev-3.0` (7,741 cached reactions, 511 follows and a completed sync), while the
running review server selected `data-test-community` (400 reactions, an incomplete
sync and 30 community recommendations). Both contained protected credentials.
Switching paths appeared to lose the session and profile; no migration or merging
was needed. Neither directory has been reset or merged.

Startup also waited for first analysis before opening the app. Auth-status performed
a synchronous network refresh before returning cached identity. An incomplete sync
had no durable cursor. OAuth refresh replaced the previous token payload, losing
refresh tokens or scope grants when the response omitted unchanged fields. Temporary
refresh failures were not distinguished from an invalid grant.

The existing 2.x DPAPI, refresh lock, account isolation and SQLite design were reused
in this separate clone. No 2.x credentials or databases were copied. Bounded public
tag inventories were read from the existing metadata collection in read-only mode
and added to the existing 3.0 sample; the source file size and modification time
remained unchanged.

## Persistence architecture and behavior

The ignored `.data-directory-3.0.json` pins this workstation to the already-running
review profile, `data-test-community`. Python startup and the PowerShell launcher
honor the same selection. Environment variables and explicit launcher directory
arguments remain available. The separate, fuller `data-dev-3.0` profile is untouched.

OAuth tokens remain encrypted with Windows DPAPI, atomically replaced on refresh.
No tokens enter browser storage, gallery cache files, screenshots or logs. Identity
renders before network refresh. A temporary outage retains the protected session;
`invalid_grant` persists a reauthentication marker while retaining cached identity
and profile. Writes are disabled until the session is usable. Mocked credentials
were used for automated auth tests; real OAuth grants were not exercised.

Profile SQLite survives restarts and frontend changes. Durable sync checkpoints
resume interrupted reaction listings for up to 24 hours; only completed listings
reconcile removals. New images receive tag lookups while existing tags are reused.
An account switch snapshots the previous 3.0 profile before clearing active tables.
Partial profiles are labeled honestly. Cached daily blocks, including half-days,
open through the existing gallery pipeline. Without a cached block, My Profile
opens immediately. Community does not wait for analysis. Opening the app never
starts a new artwork-day download or count estimate. The established 24-hour
background profile refresh remains; recent failed attempts have a retry cooldown.

`cache/community-metadata.sqlite3` stores public artwork metadata, account-scoped
controls and member-scoped gallery/status snapshots with verification and attempt
timestamps. Default freshness is 86,400 seconds. Fresh metadata is reused; stale
metadata renders immediately while a deduplicated background refresh runs. Failures
retain prior values and impose a retry cooldown. Manual Refresh queues revalidation.
Cache timestamps and stale/pending status are visible. Cached allowance is advisory:
submission always rechecks current eligibility, identity and quotas at the backend.

Every gallery response and thumbnail request applies current global rating, hidden
artist, hidden image and hidden tag controls. Cached metadata is not authority for
submission. New accounts cannot reuse another account's cached controls. Unknown
tag inventories fail closed when hidden topics exist. Local content-control actions
update the Community control snapshot immediately; cross-tab invalidation remains.

Thumbnails reuse `history.preview_url` with width 512 and persist separately on disk.
Downloads accept only approved image types and at most 2 MiB. CDN browser headers
avoid its non-browser 1010 rejection. The only supported redirect is to Civitai's
HTTPS public blob store. Legacy redirects are accepted only after a bounded header
check confirms an already-small image; oversized originals are rejected before the
remaining body is read. Cached bytes are never served without checking controls.
Browser responses use `no-store` so a policy change cannot expose browser-cached media.

The gallery reuses Discovery cards, detail interaction and original artwork links.
Recommend Art opens one compact modal containing the URL/ID field, rules and remaining allowance. One submit verifies and commits; there is no preview/confirmation stage. Attribution and dates
remain visible on cards. The member cookie persists across browser/server restarts.

## Limits and remaining work

Real OAuth refresh/revocation and production Supabase/Postgres integration were not
run against live accounts; production integration explicitly skips without an isolated
endpoint and test-account credentials. No cloud resources were created.

An initial uncached production lookup still needs the upstream service; cached reads
survive later outages. Stale metadata can reflect an upstream change until background
refresh completes. Quotas and submission eligibility remain authoritative at confirm.

The current 8907 profile hides 117 tags and 145 creators. Existing recommendations
without a complete matching tag snapshot remain withheld. The real-art screenshots
use a separate PG/PG-13 simulated viewer; personal restrictions were not weakened to
produce screenshots. Cached fixture metadata and simulated artist identifiers remain
development evidence, never production ownership attestations. Public live verification
attempts returned authorization errors; they failed closed without sending real tokens.
