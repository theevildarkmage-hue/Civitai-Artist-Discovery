# Local stable-readiness workflow

This workflow prepares stable 3.0.1 locally. It does not authorize publication,
Git history migration, hosted configuration changes or Production activation.
Existing stable users use normal automatic updates. Beta users may manually copy
the documented local-data allowlist; no new beta bridge is mandatory. A beta.15
build is used only for the second compiled credential-regression channel.

Maintainer identity checks/builds require the approved private policy configured
outside the worktree. Never publish that policy or provide it to arbitrary source
users. Running the application from source does not require it.

## Repeatable release gate

Use the project virtual environment for source tests. Node requires
`--experimental-transform-types`; the gate supplies it. Profiles and ports are
owned disposable test resources. No real OAuth profile or hosted record is used.

```powershell
python scripts/release-test-gate.py --output ../local-gate-new
```

For the complete available owned PostgreSQL/Edge tier, add `--native`, `--bin`
(PostgreSQL bin directory), `--http-deno` (Deno executable) and `--http-postgrest`
(PostgREST executable). The gate retains source fingerprints, per-test logs,
Python/Node results and native receipts. Supply repeated --package arguments for
both clean nonpreview Development beta and Production stable folders; full acceptance
requires both frozen credential-isolation suites and provenance checks.
Skipped/unavailable prerequisites remain
explicit; a source-only pass does not certify packaged OAuth or Production.
Evidence must be outside the source worktree and use a fresh output directory;
the gate rejects an in-tree output so generated evidence cannot alter its inputs.
Do not remove fail-closed tag/authentication assertions to make fixtures pass.

## Build and prepare portable packages

Use the reviewed Windows Python 3.14.8+ / OpenSSL 3.5.9+ release interpreter.
Use clean local commits and a fresh output directory per build. Generated static
assets, configuration and resources stay outside tracked source. No existing
output, profile, backup or stable installation is deleted by the release wrapper.

```powershell
# Unpublished nonpreview Development credential-regression package.
./scripts/release.ps1 -Channel beta -Version 3.0.0-beta.15 -Environment development -ProjectRef aibelmhucizupzvvhdvf -PythonExecutable <reviewed-python.exe> -OutputRoot <fresh-beta-directory>

# Unpublished nonpreview Production stable candidate.
./scripts/release.ps1 -Channel stable -Version 3.0.1 -Environment production -ProjectRef masrxykkbqngtbeeqpbq -PythonExecutable <reviewed-python.exe> -OutputRoot <fresh-stable-directory>
```

Beta uses `CivitaiDiscoveryBeta/CivitaiDiscoveryBeta.exe`; stable uses the canonical
`CivitaiArtistDiscovery/CivitaiArtistDiscovery.exe` expected by 2.2.1. Artifact
preparation emits the matching ZIP, release identity, source/configuration
provenance, manifest and SHA-256 sums. The old prepare-beta-artifacts entry point
delegates to the shared preparer. Preview identities remain rejected by updater
verification; do not relabel them as real releases.

When publication is separately approved, GitHub release `target_commitish` must
be the full immutable 40-character source commit (for example, the explicit
`gh release create --target <full-commit-sha>` argument), not a branch name.
Use the canonical channel ZIP and matching embedded release identity. Stable
releases must be non-prereleases; bridge betas remain prereleases. The local
release script prepares files only and never pushes, tags or publishes.

A real Production build requires `-Environment production -ProjectRef <approved
distinct-production-reference>` and stable channel. No URL, token, profile setting
or runtime environment variable can repoint the compiled client. All three
Community clients share `discovery/build_config.py`. Packaged configuration is
required, validated, and included in provenance. Development beta builds retain
the existing reviewed project. A stable Development build requires preview mode
and labels itself Development Preview. These local build commands do not provision
or activate a hosted project.

Use `inspect-production-package.py --package <folder> --output <fresh-report>`
and `validate_packaged_updater.py <folder> --browser` for actual frozen package
inspection, isolated startup/browser checks and real Windows locked-file rollback.
An upgrade-profile check must use an explicitly disposable copy; never pass an
existing installation's profile or stored OAuth credentials.

## Historical beta graduation and interrupted updates

The following explains retained helper recovery, not a new mandatory bridge. For
manual beta-to-stable recovery use the current installation guide and bundled
SQLite backup helper. Never restore exposed Git ancestry as public rollback.


The bridge recognizes canonical stable 3.x releases and validates channel,
application identity, immutable tag/source, digest and archive safety. It stages
and launches the stable executable explicitly, preserving portable data. The old
beta executable is retired inside the rollback journal. Existing manually created
shortcuts must be updated to the stable executable after graduation.
The helper retains the running parent's custom HTTP port from its own PID-bound
instance record before waiting for shutdown. Only a validated integer port is
passed to the new executable; stale or invalid records retain the old default
launch behavior. This supports automatic relaunch without redirecting another
installation or trusting a URL as a command.

If a helper is forcibly terminated during replacement, preserve `data/update`
and the backup. Re-run the retained staged executable with:

```powershell
<retained-staged-executable.exe> --apply-update <portable-data>/update/apply.json
```

Only use the original matching helper/configuration. It validates the retained
journal and restores interrupted entries before retrying. Do not delete the
journal/backup or invent a new path/configuration to bypass recovery checks.
Unattended OS-level repair of an unstartable runtime is not claimed.

## Historical initial Production preparation

This initial bootstrap record is historical. A maintenance release must not
reinitialize, reset, disable or redeploy Production as part of publication.


Use the single maintained [health/export/restore procedure](3.0-recovery.md) and
the [versioned Production bootstrap](3.0-production-bootstrap.md). Development's
16-migration manifest preserves applied history, including persistent invitations.
The clean Production profile starts disabled and contains no personal test quota
exceptions or seeded member/audit history. Do not copy beta device/session/replay
or personal records into Production without a specific owner migration decision.

## Capture-default compatibility decision

Explicit settings are preserved. A genuinely fresh installation retains its
established defaults. Existing profiles in either channel default missing automatic
capture off and missing collection coverage to their saved viewing ceiling, so a
bridge update cannot persist broader inferred values before stable graduation.
Empty, malformed and non-object settings use conservative fallback values and are
not rewritten merely by reading them. An explicit settings save retains their
original bytes in a separate local invalid-settings backup before replacement.
No recovery of unknowable lost preferences is claimed; restoring known preferences
or selecting new ones remains the user's choice. No consent UI or account workflow
is introduced.
