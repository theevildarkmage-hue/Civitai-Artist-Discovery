# Local stable-readiness workflow

Published Windows beta: 3.0.0-beta.13. Local bridge source: 3.0.0-beta.14.
Neither the bridge nor stable 3.0 is published by these commands. Stable 2.2.1
remains separate. Production provisioning, billing, public activation and release
publication require separate owner approval.

## Repeatable release gate

Use the project virtual environment for source tests. Node requires
`--experimental-transform-types`; the gate supplies it. Profiles and ports are
owned disposable test resources. No real OAuth profile or hosted record is used.

```powershell
python scripts/release-test-gate.py --output reports/local-gate
```

For the complete available owned PostgreSQL/Edge tier, add `--native`, `--bin`
(PostgreSQL bin directory), `--http-deno` (Deno executable) and `--http-postgrest`
(PostgREST executable). The gate retains source fingerprints, per-test logs,
Python/Node results and native receipts. Skipped/unavailable prerequisites remain
explicit; a source-only pass does not certify packaged OAuth or Production.
Do not remove fail-closed tag/authentication assertions to make fixtures pass.

## Build and prepare portable packages

Use the reviewed Windows Python 3.14.8+ / OpenSSL 3.5.9+ release interpreter.
Use clean local commits and a fresh output directory per build. Generated static
assets, configuration and resources stay outside tracked source. No existing
output, profile, backup or stable installation is deleted by the release wrapper.

```powershell
# Unpublished Development bridge preview.
./scripts/release.ps1 -Channel beta -Version 3.0.0-beta.14 -Environment development -Preview -PythonExecutable <reviewed-python.exe> -OutputRoot <fresh-beta-directory>

# Stable executable/layout acceptance without choosing a Production account.
./scripts/release.ps1 -Channel stable -Version 3.0.0 -Environment development -Preview -PythonExecutable <reviewed-python.exe> -OutputRoot <fresh-stable-directory>
```

Beta uses `CivitaiDiscoveryBeta/CivitaiDiscoveryBeta.exe`; stable uses the canonical
`CivitaiArtistDiscovery/CivitaiArtistDiscovery.exe` expected by 2.2.1. Artifact
preparation emits the matching ZIP, release identity, source/configuration
provenance, manifest and SHA-256 sums. The old prepare-beta-artifacts entry point
delegates to the shared preparer. Preview identities remain rejected by updater
verification; do not relabel them as real releases.

A real Production build requires `-Environment production -ProjectRef <approved
distinct-production-reference>` and stable channel. No URL, token, profile setting
or runtime environment variable can repoint the compiled client. All three
Community clients share `discovery/build_config.py`. Packaged configuration is
required, validated, and included in provenance. Development beta builds retain
the existing reviewed project. A stable Development build requires preview mode
and labels itself Development Preview. No Production project was created here.

Use `inspect-production-package.py --package <folder> --output <fresh-report>`
and `validate_packaged_updater.py <folder> --browser` for actual frozen package
inspection, isolated startup/browser checks and real Windows locked-file rollback.
An upgrade-profile check must use an explicitly disposable copy; never pass an
existing installation's profile or stored OAuth credentials.

## Beta graduation and interrupted updates

The bridge recognizes canonical stable 3.x releases and validates channel,
application identity, immutable tag/source, digest and archive safety. It stages
and launches the stable executable explicitly, preserving portable data. The old
beta executable is retired inside the rollback journal. Existing manually created
shortcuts must be updated to the stable executable after graduation.

If a helper is forcibly terminated during replacement, preserve `data/update`
and the backup. Re-run the retained staged executable with:

```powershell
<retained-staged-executable.exe> --apply-update <portable-data>/update/apply.json
```

Only use the original matching helper/configuration. It validates the retained
journal and restores interrupted entries before retrying. Do not delete the
journal/backup or invent a new path/configuration to bypass recovery checks.
Unattended OS-level repair of an unstartable runtime is not claimed.

## Recovery and Production preparation

Use the single maintained [health/export/restore procedure](3.0-recovery.md) and
the [versioned Production bootstrap](3.0-production-bootstrap.md). Development's
16-migration manifest preserves applied history, including persistent invitations.
The clean Production profile starts disabled and contains no personal test quota
exceptions or seeded member/audit history. Do not copy beta device/session/replay
or personal records into Production without a specific owner migration decision.

## Capture-default compatibility decision

Explicit settings are preserved. Beta and true first-install defaults remain
owner-approved. Stable builds conservatively inherit the viewing capture ceiling
and default automatic capture off for an existing valid nonempty preferences file
missing those values. Empty and malformed files retain their existing defaults;
non-object JSON now safely uses those malformed-file defaults instead of crashing.
Their treatment as an upgrade versus fresh install remains an owner
policy decision. No consent UI or new account workflow is introduced.
