## Restricted operator lifecycle and hosted blocker

`scripts/provision-community-operator.py` implements create/rotate/disable/revoke.
Supply the approved administrator connection through a secure child environment
(`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, verified TLS for remote).
Supply a newly generated 32–256 character password through
`COMMUNITY_OPERATOR_NEW_PASSWORD`, never command arguments or files. Use a
`cad3_operator_...` login, verified stable member ID on create, UTC expiry at most
30 days, and a bounded reason. Never print the environment or record SQL input.
Remote use additionally requires separate approval and `--allow-remote`; the flag
does not itself authorize a connection.

The authenticated administrator must already have an independently verified,
unexpired private operator mapping. Initial administrator enrollment requires its
own reviewed identity check and approval; this script does not bootstrap trust
from caller-supplied identity. Audit actor/login derive from session_user, while
the supplied member ID identifies only the target. Restricted logins are
NOINHERIT, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOREPLICATION, NOBYPASSRLS.
The group has no parent authority. No browser/runtime service credential is an
operator credential.

Create is transactional. Rotation disables the login and mapping first, commits,
terminates that login's sessions in the selected database, then replaces its
credential/expiry and reactivates it. Interruption leaves it disabled. Disable
retains evidence; revoke additionally clears the password and membership.
Inventory other databases separately: session termination here is deliberately
limited to the selected database. Validate with a fresh dedicated operator
connection, ordinary-runtime denial, old-password denial and audit actor/reason;
never test by embedding the password in a client request.

Local lifecycle tests demonstrated creation, rotation, existing-session
termination, old-password rejection, emergency disable/recovery, revocation and
audit attribution. **Hosted provisioning is blocked with the current tool.**
Read-only catalog checks show hosted postgres has CREATEROLE, is not superuser and
cannot SET log_statement or log_min_error_statement. The tool requires these
transaction-local logging protections and refuses unsafe audit transport before
sending a credential-bearing CREATE/ALTER ROLE statement. Removing those checks
would lose the reviewed confidentiality guarantee. Native superuser success does
not establish hosted compatibility. No hosted provisioning was attempted.

Minimum correction: establish and review a provider-supported provisioning and
logging/redaction path for this restricted credential, or separately review a
different isolated moderator-service architecture. Confirm actual log handling
with synthetic local credentials before any approved hosted enrollment. Do not
grant broad/superuser rights or weaken logs speculatively. The Management API's
experimental CLI login-role endpoint accepts a read_only flag; it is not a
documented arbitrary least-privileged moderator provisioner and must not replace
this credential with a more powerful temporary CLI login.

Compromise: stop moderator work, use an independently authorized administrator to
disable that exact login/mapping and terminate its sessions, preserve audit and
incident timestamps, assess affected actions, and rotate through the reviewed
transport. Confirm revoked sessions and old credentials fail before re-enrollment.
If administrator authority is unavailable, escalate to the owner/provider and
keep beta disabled; do not use a service-key fallback. No hosted emergency drill
is claimed here.

## Encrypted backup and compatible recovery

The native rehearsal pipes pg_dump custom-format output into memory and encrypts
it with Windows account-bound DPAPI. No plaintext dump or key file is written.
It verifies SHA-256, rejects a tampered archive, checks the decrypted archive TOC
and restores transactionally into a separate database in the owned cluster.
All twelve table hashes, derived weekly quota, migration versions/names/statement
hashes, ownership, grants, RLS and function fingerprints must match. The encrypted
fixture archive and fingerprints are in the ignored evidence directory.

This proves a separate-database restore, not independent-machine disaster recovery:
roles/passwords are cluster-global and already exist in this cluster. An approved
hosted recovery plan must separately recreate restricted role definitions and
secure credentials, retain role/owner mappings, restore required extensions and
app configuration, and validate cross-host permissions. DPAPI depends on this
Windows account/key availability; establish an independently recoverable approved
backup custody mechanism before relying on it for production recovery. Restore
only into an isolated target, never over a running personal/application database.

Owner confirms the staging plan is **Free**. The read-only backup API reports
physical backup machinery enabled, PITR disabled and zero listed backups. These
facts do not establish an available recovery point. Supabase recommends regular
independent exports for Free projects. Its daily backups omit custom-role
passwords, and database backups omit Storage objects. No hosted backup/export,
restore, password retrieval or settings change was performed. Before deployment,
approve an encrypted hosted export and isolated restore with explicit custody,
retention and proposed RPO 24 hours/RTO 4 hours; these targets are not measured.
