# 2.0 local acceptance build

This is the `v2` working preview, not a published release. The executable still reports
the 1.0.4 engine version. Keep distributing v1 from the separate `main` worktree until
the preview has been accepted; do not upload this internal package as a stable update.

## What to test

1. Open the calendar in the command bar. Choose a saved date, switch All day/Morning/Evening,
   and try Latest saved. An unbuilt date should offer Build gallery without starting it.
   Refresh a built day, then compare first-preview speed with your previous app.
2. Switch For You / Popular / Followed First / New to You / Emerging First. Scroll down,
   refresh, and confirm the selected view, model filters, and browsing position return.
3. Open Filters. Search for a model, expand the full list, choose two models, remove one chip,
   and reset. Reset should leave only
   PG and PG-13 enabled and no model refinement. Changing ratings must retain models.
4. Open the gear and move the Card size and discovery-threshold sliders. Check Large /
   Medium / Small cards. Try arrows, details, original-image links, reactions,
   and Follow. These last two intentionally change your Civitai account when you click.
5. Open Time Machine. Confirm creator progress, old artwork, shared cards, and details.
   Scrolling past a card intentionally records progress. Check Stop during history reading.
6. Open My Profile. Check Worth Following, metrics, and Settings below the insights.
   Do not use Delete this data unless you intend to remove your local analysis.
7. Use keyboard Tab, Enter, Down, and Escape on Filters, preferences, and details. Resize
   to a narrow window and try browser zoom. Report clipped controls or unreadable overlays.
8. Close using Close app and launch again. Check the tray, account state, and saved data.

## Verification and remaining gates

- The integration suite passed all 74 scripts, including calendar and command-bar coverage.
- Current synthetic screenshots are under `reports/v2/current/`, with no horizontal
  overflow. Package validation results are recorded in the checkpoint.
- User visual/usability acceptance, manual tray/relaunch review, and beta feedback are
  still required. Publishing, version promotion, and merging to `main` are not performed.
- The repository's target architecture is incremental, not an all-at-once rewrite.
  Collection/authentication orchestration remains in `app.js`; existing base CSS remains
  beneath the shared tokens/component styles. Further cosmetic source cleanup is not a
  substitute for acceptance testing and must not destabilize the working workflows.

## Performance evidence and limits

Offline fixture: warm first preview 187 ms; feed changes 25–41 ms; model refinement 110 ms;
content refinement 76 ms; deep restore retained 74 cards. Cold-tag fixture: 256 ms to
skeleton and 591 ms to image load, including an explicit 250 ms tag delay. The 200 ms
cold-skeleton target is still a miss; follow up by parallelizing startup summary/status
reads without weakening onboarding/content verification. Timings vary with machine load.

Real archive before the final index: first preview frame 7,499 ms in a fresh browser,
4,225 ms on refresh, while the regression suite and background collection were running.
Day-summary requests took 4,480 / 823 ms and first artist requests 1,460 / 1,746 ms.
These are observed runs, not a controlled broadband benchmark or a final speed claim.

The hidden-tag query scanned 3,869,527 tag rows. A disposable database snapshot measured
611.76 ms before versus 55.94 ms with the new index/query, with identical decisions for
all 68,515 matching images. This is an 11× query improvement, not an 11× whole-app claim.
The running app must restart before it uses the new query. Repeat real-browser timing
after restart and without concurrent background jobs before accepting the latency targets.

```powershell
py scripts/measure_hidden_tags.py data/discovery/taste.sqlite3
py scripts/measure_preview.py http://127.0.0.1:PORT --date YYYY-MM-DD
```

The browser probe blocks writes except tag-verification reads, uses Popular to avoid
starting ranking preparation, and saves no artwork/screenshots. `?uiPerf=1` also exposes
`window.CivitaiPerformance.snapshot()` for local diagnostics. It records aggregate timing
and API paths, not query strings, image URLs, prompts, or account identifiers. Cross-origin
image byte sizes may be unavailable, and first-preview frame means the animation frame
after image load, not a compositor paint measurement. Diagnostics are never uploaded.

## Shared component map

- `ui/bootstrap.js`: module loading and the explicit controller-services bridge.
- `ui/shell.js`, `pages.js`: shared header, navigation, toolbar grouping, Settings placement.
- `ui/cards.js`, `artwork.js`: Gallery/Time Machine card behavior, carousel, safe previews.
- `ui/creator-actions.js`: Follow transaction shared by cards and Profile rows.
- `ui/profile.js`: Profile presentation; services are injected by its page adapter.
- `ui/state.js`: validated browsing snapshot, model query encoding, session reading.
  Rating restoration remains governed by saved account settings, never an untrusted tab.
- `ui/filters.js`, `menu.js`, `dialog.js`, `feedback.js`: reusable interaction/feedback rules.

New tabs should compose these modules and supply page-specific services/data. Do not
copy the card controller or Follow transaction into a new page. Existing server/controller
adapters are deliberate integration boundaries, not a second component implementation.

## Data compatibility and rollback

The only added schema object in this final pass is the `archive_tags_name_image` SQLite
index. It is additive: v1 can ignore/use it, and no archive/account rows are transformed.
Older-schema and data-preservation tests remain covered. No new account-data migration
or credential storage change is introduced by the UI refresh.

Close the app before switching versions; never run v1 and v2 against the same data folder
at once. For an acceptance test involving a separate data copy, close the app first and
copy the entire portable `data` folder, not just individual SQLite files. Keep that backup
private because it contains account-derived data. The automated package smoke uses only
disposable data. Real-data rollback with both app versions remains a manual acceptance gate.
